# 메시지와 알림

계약마다 당사자 둘만의 대화방이 하나 있고, 계약·마일스톤 이벤트가 시스템 메시지로 그 안에 기록된다. 알림은 인앱과
이메일 두 채널로 가고, 거래와 돈에 관한 알림은 끌 수 없다. 메시지는 인앱 알림을 만들지 않고, 읽지 않은 메시지가
쌓이면 묶음 이메일(다이제스트)로 알린다.

## 대화방

- 지원 수락 트랜잭션이 계약과 함께 대화방을 만든다. 참여자는 그 계약의 의뢰인과 프리랜서 **두 명뿐이고 바뀌지 않는다.**
  역할과 상관없이 참여자만 들어올 수 있다.
- 메시지는 둘 중 하나다. `TEXT`는 참여자가 쓴 글이고, `SYSTEM`은 발신자 없이 이벤트를 기록한 글이다.
- 실시간 채널은 없다. 클라이언트가 폴링한다. 열린 대화는 화면이 보이는 동안 5초마다 새 메시지를, 안 읽은 메시지
  배지는 30초마다 센다. 대화방 조회는 아무것도 쓰지 않으므로 폴링이 DB를 바꾸지 않는다.

| 정책 | 값 | 기준 |
| --- | --- | --- |
| 본문 | 앞뒤 공백 제거 후 5,000자 이하. 첨부가 없으면 1자 이상 | `MAX_MESSAGE_LENGTH`, `src/schemas/conversations.ts` |
| 첨부 | 메시지당 최대 5개, 각 10MB. 이미지, PDF, ZIP, 텍스트, 오피스 문서, HWP | `src/middlewares/attachmentUpload.ts` |
| 삭제 가능 시간 | 보낸 뒤 5분 미만 | `DELETE_WINDOW_MS`, `src/services/messaging.service.ts` |
| 계약 완료 후 대화 | 완료 시각부터 30일(정확히 720시간)까지 | `POST_COMPLETION_WINDOW_MS` |
| 메시지 한 페이지 | 기본 30, 최대 100 | `DEFAULT_MESSAGE_PAGE`, `MAX_MESSAGE_PAGE` |

### 누가 보낼 수 있나

위에서부터 처음 맞는 줄이 정한다. 읽기, 읽음 처리, 내 메시지 삭제는 어느 경우에도 된다. 시스템 메시지는 이 규칙과
상관없이 항상 기록된다. 닫힘 규칙은 사람에게 적용되고 이벤트에는 적용되지 않는다.

| 조건 | 보내기 | 이유 표시(`closedReason`) |
| --- | --- | --- |
| 계약이 완료됐고 완료 후 30일이 지났다 | 불가 | `CONTRACT_CLOSED` |
| 상대방이 탈퇴했다 | 불가 | `COUNTERPART_INACTIVE` |
| 그 밖(서명 대기, 진행 중, 완료 후 30일 안) | 가능 | 없음 |

- 상대방이 탈퇴해도 대화방, 메시지, 상대 이름은 그대로 보인다. 바뀌는 것은 보내기뿐이다.
- 프로젝트가 삭제된 계약의 대화방은 없는 것과 같다. 목록과 안 읽은 메시지 합계에서도 빠진다.

### 메시지 순서와 삭제

- 한 대화방 안에서 메시지 시각(`createdAt`)은 커밋 순서대로 **엄격히 증가한다.** 폴링 커서와 읽음 표시가 이것에
  기댄다. 시각은 항상 서버 시계다. 미래 시각으로 돈 작업이 남긴 시스템 메시지도 실제로 쓴 순서대로 정렬된다.
- 메시지는 고칠 수 없다. 보낸 사람이 5분 안에 지울 수 있고, 지운 메시지는 본문과 첨부가 빈 표시(tombstone)로 남는다.
  행과 첨부 파일은 저장소에 그대로 있다. 첨부는 공개 URL이다. 첨부를 비공개 버킷과 서명 URL로 옮길지, 메시지를 지우면
  파일도 지울지는 정하지 않았다([#22]).

### 안 읽은 메시지와 읽음 표시

- 안 읽은 수는 **상대방이 보낸, 지우지 않은 `TEXT` 메시지** 중 내 읽음 표시(`lastReadAt`)보다 새것의 개수다.
  시스템 메시지와 내 메시지는 세지 않는다. 세다가 지워진 메시지는 빠진다.
- 대화를 연다고 읽음이 되지 않는다. 화면이 새 상대 메시지를 보여준 뒤 읽음 처리를 부르면, 표시가 상대의 가장 최근
  메시지 시각으로 옮겨진다. 표시는 뒤로 가지 않는다. 시스템 메시지는 표시를 옮기지 않는다.
- 내가 보낸 메시지에는 상대가 읽었는지(상대의 읽음 표시가 그 메시지 시각 이후인지)를 함께 보여준다.

## 시스템 메시지

이벤트를 일으킨 트랜잭션 안에서, 그 트랜잭션의 **마지막 쓰기**로 남긴다. 각 이벤트는 정확히 한 번 기록된다. 경합에서
진 쪽이나 아무것도 하지 않은 결제 처리는 남기지 않는다. 문구는 한국어 고정 문장이다.

| `systemEvent` | 남기는 때 |
| --- | --- |
| `CONTRACT_CREATED` | 지원 수락 |
| `MILESTONE_PLAN_UPDATED` | 모든 계획 교체(서명이 있었는지와 상관없이, 알림과 다르다) |
| `CONTRACT_ACTIVATED` | 계약을 시작시킨 서명 |
| `MILESTONE_FUNDED` | 마일스톤을 실제로 결제 상태로 바꾼 결제 |
| `MILESTONE_SUBMITTED`, `MILESTONE_REVISION_REQUESTED` | 제출, 반려 |
| `MILESTONE_APPROVED`, `MILESTONE_AUTO_APPROVED` | 수동 승인, 자동 승인 |
| `CONTRACT_COMPLETED` | 계약 완료(그 승인의 메시지 다음) |

프로젝트가 삭제된 계약의 자동 승인은 시스템 메시지를 남기지 않는다.

## 알림

알림은 모두 `notify()` 계열(`src/lib/notifications/notify.ts`)로만 만들고, 상태 변경의 트랜잭션 안에서 인앱 행,
이메일 발송 기록, 발송 작업을 함께 쓴다. 변경이 롤백되면 알림도 메일도 없다. 탈퇴한 사용자에게는 보내지 않는다.

- 알림은 받는 사람 본인만 보고 읽음 처리한다. 남의 알림 id는 없는 것과 같아서 id를 떠보는 데 쓸 수 없다.
- 읽음 처리는 멱등이다. 다시 읽어도 처음 읽은 시각을 유지한다. "모두 읽음"은 안 읽은 것만 바꾼다.
- 안 읽은 알림 수는 지금 보이는 페이지가 아니라 전체를 센다.

### 채널 정책

타입마다 받는 사람과 채널별 기본값, 그리고 받는 사람이 바꿀 수 있는지가 정해져 있다(`NOTIFICATION_POLICY`,
`src/lib/notifications/policy.ts`). **잠긴** 채널은 바꿀 수 없다. 원칙은 이렇다.

- 거래와 돈에 관한 알림(수락, 서명, 결제, 제출, 판단, 지급)은 **인앱이 잠겨 있다.** 누구도 놓치면 안 된다.
- 돈이 자동으로 움직이거나 지급에 문제가 생겼음을 알리는 세 가지(자동 승인 예고, 지급 보류, 지급 실패)는 **이메일도 잠겨 있다.**
- 미확인 메시지 다이제스트는 이메일 전용이다. 메시지는 대화방에서 보므로 인앱은 꺼진 채로 잠겨 있다.

| 타입 | 받는 사람 | 인앱 | 이메일 |
| --- | --- | --- | --- |
| `APPLICATION_CREATED` | 의뢰인 | 켬 | 켬 |
| `APPLICATION_ACCEPTED` | 프리랜서 | 켬, 잠김 | 켬 |
| `APPLICATION_REJECTED`, `PROJECT_STATUS_CHANGED` | 프리랜서 | 켬 | 끔 |
| `CONTRACT_ACTIVATED`, `CONTRACT_COMPLETED` | 양측 | 켬, 잠김 | 켬 |
| `MILESTONE_PLAN_UPDATED`, `MILESTONE_FUNDED`, `MILESTONE_REVISION_REQUESTED`, `MILESTONE_APPROVED` | 프리랜서 | 켬, 잠김 | 켬 |
| `MILESTONE_SUBMITTED` | 의뢰인 | 켬, 잠김 | 켬 |
| `MILESTONE_AUTO_APPROVED` | 양측 | 켬, 잠김 | 켬 |
| `MILESTONE_AUTO_APPROVE_REMINDER` | 의뢰인 | 켬, 잠김 | 켬, 잠김 |
| `MILESTONE_DUE_SOON` | 프리랜서 | 켬 | 켬 |
| `MILESTONE_OVERDUE` | 양측 | 켬 | 켬 |
| `SETTLEMENT_SCHEDULED` | 프리랜서 | 켬 | 끔 |
| `SETTLEMENT_PAID` | 프리랜서 | 켬, 잠김 | 켬 |
| `SETTLEMENT_ON_HOLD`, `SETTLEMENT_FAILED` | 프리랜서 | 켬, 잠김 | 켬, 잠김 |
| `MESSAGE_UNREAD_DIGEST` | 양측 | 끔, 잠김 | 켬 |

인앱 알림은 위 19종이고, 다이제스트까지 20종이다. 설정 화면에는 내 역할이 받는 타입만 나온다(의뢰인 8종, 프리랜서 17종).

### 알림 설정

- 실제 채널은 이렇게 정한다. 잠긴 채널은 항상 정책 기본값이다. 잠기지 않은 채널은 사용자가 고른 값이 있으면 그것,
  없으면 기본값이다. 역할은 상관없다.
- **기본값과 다른 것만 저장한다.** 채널 값이 기본값과 같거나 잠긴 채널이면 저장하지 않고(null), 두 채널이 모두 기본값이면
  행을 지운다. 그래서 나중에 기본값을 바꾸면 손대지 않은 모든 사용자에게 반영된다.
- 설정 변경은 부분 갱신이다. 보내지 않은 타입과 채널은 그대로다. 잠긴 채널을 끄려는 요청은 거절하고, 잠긴 채널을
  원래 값으로 보내는 것은 통과한다(화면이 받은 설정을 그대로 돌려보낼 수 있다). 하나라도 잘못되면 아무것도 저장하지 않는다.
- 설정은 알림을 만드는 순간 한 번 읽는다. 나중에 바꿔도 이미 만든 발송을 취소하거나 놓친 것을 새로 만들지 않는다.
- 내 역할이 받지 않는 타입의 설정도 저장되고 남는다. 역할이 바뀌어도 유지된다. 탈퇴 후 복구하면 다시 적용된다.

## 이메일

- 이메일이 켜져 있고 받는 사람이 탈퇴하지 않았고 주소가 있으면, `notify()`가 발송 기록(`EmailDelivery`)과 발송 작업을
  만든다. 주소는 만든 시점의 주소로 고정된다. 제목은 `[WorkBridge] <제목>`, 본문은 내용, 바로가기 링크, 알림 설정 링크다.
- 발송 기록은 `PENDING`에서 `SENT`, `FAILED`, `SKIPPED` 중 하나로 **한 번만** 바뀐다. 보내기 전에 받는 사람이 탈퇴했으면
  `SKIPPED`다. 발송은 최소 한 번이다. 공급자가 받았는데 기록이 실패하면 다시 보낼 수 있어서, 발송 기록 id를 중복 방지
  키로 공급자에게 넘긴다.
- 모든 메일은 내 계정에서 일어난 일에 대한 거래성 메일이다. 그래서 수신 거부 링크가 없고, 본문 마지막 줄이 로그인해야
  하는 알림 설정 화면을 가리킨다.
- 지금 실제 메일 서비스는 연결돼 있지 않다. 기본 provider는 메일 한 통을 `mail.sent` 로그 한 줄로 남긴다. 운영에서는
  메일 작업이 플래그로 꺼져 있다([jobs.md](jobs.md#플래그로-꺼-둔-작업)).

### 미확인 메시지 다이제스트

메시지마다 메일을 보내지 않고, 읽지 않은 메시지를 모아 한 통으로 알린다(`src/jobs/handlers/messageDigest.ts`).

| 정책 | 값 | 기준 |
| --- | --- | --- |
| 지연 | 메시지 후 10분. 그 안에 읽으면 메일이 가지 않는다 | `UNREAD_DIGEST_DELAY_MS` |
| 빈도 제한 | 대화방·받는 사람마다 60분에 최대 한 통 | `UNREAD_DIGEST_THROTTLE_MS` |

- 메시지를 보내면 상대방 몫의 다이제스트 작업을 10분 뒤로 잡는다. 이미 대기 중인 작업이 있으면 새로 잡지 않는다.
- 작업이 돌 때 안 읽은 메시지가 없으면 끝난다. 가장 오래된 안 읽은 메시지가 아직 10분이 안 됐으면(앞 메시지는 읽고 새
  메시지가 온 경우) 그 메시지 기준 10분 뒤로 다시 잡는다.
- 마지막 다이제스트가 60분 안이면 보내지 않고 정확히 60분 되는 시각으로 다시 잡는다. 그 사이에 쌓인 메시지는 그때 한
  통으로 나간다. 예: 메시지 A(t0) → t0+10분 다이제스트 → 메시지 B(t0+20분) → t0+70분에 B를 담은 다이제스트.
- 받는 사람이 다이제스트 메일을 끄면 아무것도 만들지 않는다.
