# 계정과 프로필

사용자는 가입할 때 의뢰인 또는 프리랜서 중 하나의 역할을 고르고, 역할마다 다른 프로필을 채운다. 프리랜서는
포트폴리오와 경력으로 자신을 소개한다. 인증은 상태 없는 토큰이라 로그아웃이 즉시 모든 토큰을 무효화하지는 않는다.

## 가입과 로그인

- 가입에는 이메일, 비밀번호, 이름, 역할(`CLIENT` 또는 `FREELANCER`)이 필요하다. 이메일은 계정마다 유일하다.
  비밀번호는 bcrypt 해시로만 저장하고 어떤 응답에도 해시를 내보내지 않는다.
- 이메일을 소문자·공백 제거로 정규화할지는 정하지 않았다([#21]). 지금은 입력한 그대로 저장하고 비교한다.
- 로그인 실패는 "없는 이메일", "비밀번호 없는 계정(Google 전용)", "틀린 비밀번호"를 구분하지 않는다. 계정이
  있는지 알아내는 데 쓸 수 없어야 한다.

### 토큰

| 토큰 | 수명 | 보관 | 기준 |
| --- | --- | --- | --- |
| 액세스 토큰 | 15분 | 클라이언트 `localStorage`, `Authorization: Bearer` | `JWT_ACCESS_EXPIRES_IN` (`src/env.ts`) |
| 리프레시 토큰 | 7일 | `httpOnly` 쿠키 | `JWT_REFRESH_EXPIRES_IN` |

- 토큰 내용은 `{ id, email, role }`이다. 갱신은 DB의 사용자 행을 다시 읽어 새 액세스 토큰을 만든다. 그래서 역할이
  바뀌면 다음 갱신부터 반영된다. 리프레시 토큰은 갱신할 때 교체하지 않는다.
- **토큰은 상태가 없다.** 로그아웃은 리프레시 쿠키를 지울 뿐이고, 이미 발급된 액세스 토큰은 만료(최대 15분)까지
  유효하다. 토큰 저장소나 차단 목록은 일부러 두지 않았다.
- 로그아웃은 인증 없이 리프레시 쿠키를 지운다. 액세스 토큰이 만료된 뒤에도 로그아웃할 수 있어야 한다(현재 다름:
  인증이 필요해 만료 뒤에는 쿠키가 남는다 [#48]).

### 로그인 요청 제한

무차별 대입을 막는 고정 윈도 제한이다. 윈도는 KST 15분 경계(:00, :15, :30, :45)에 맞춰 시작하고, 카운터는
DB에 있어서 서버 인스턴스끼리 공유한다(`src/lib/rateLimitRules.ts`).

| 규칙 | 키 | 윈도 | 한도 | 세는 것 |
| --- | --- | --- | --- | --- |
| IP별 로그인 | 클라이언트 IP | 15분 | 20회 | 결과와 상관없이 모든 로그인 시도 |
| 로그인 실패 | 이메일(공백 제거·소문자) + IP | 15분 | 5회 | 자격 증명 오류만. 성공하면 초기화된다 |

- 실패 한도에 걸리면 그 윈도가 끝날 때까지 맞는 비밀번호로도 로그인할 수 없다. 없는 이메일도 똑같이 세서 이
  제한으로 계정 존재를 알아낼 수 없다.
- 거절된 요청도 카운트에 들어간다. 클라이언트 IP를 정하는 방법은 [DEPLOYMENT.md](../DEPLOYMENT.md)와 `src/lib/clientIp.ts`에 있다.

## Google 로그인과 역할 선택

- Google 로그인은 `state` 값을 쿠키와 대조해 다른 사람의 인가 코드로 이 브라우저가 로그인되는 것(로그인 CSRF)을 막는다.
  실패는 어떤 이유든 로그인 화면의 `oauth_failed` 오류로 돌아가고 서버 오류가 되지 않는다.
- 이미 있는 계정과는 `googleId`로 연결한다. 이메일이 같다는 것만으로 비밀번호 계정에 Google 계정을 연결하지 않는다.
  주소를 실제로 소유한다는 증명이 필요하다(현재 다름: [#2]).
- 처음 들어온 Google 사용자는 프리랜서 역할로 임시 생성되고 `roleSelected: false`다. 첫 화면에서 역할을 한 번
  고른다. **역할 선택은 한 번뿐이다.** 이미 고른 사용자는 이 경로로 역할을 바꿀 수 없다. 선택하면 새 역할을 담은
  토큰을 다시 발급한다.
- 연결된 뒤에는 Google 프로필의 이메일과 이름을 다시 반영하지 않는다(의도된 동작). 이메일은 이 서비스의 로그인
  ID라 밖에서 조용히 바뀌면 다른 계정과 충돌할 수 있고, 이름은 사용자가 프로필에서 직접 고치는 값이다.
- 삭제된 계정의 이메일로는 다시 가입할 수 없고(409), 같은 이메일의 Google 로그인도 `oauth_failed`로 끝난다. 이메일이
  DB에서 유일하고 삭제된 행이 남아 있기 때문이다.

## 프로필

| 공통 | 의뢰인 전용 | 프리랜서 전용 |
| --- | --- | --- |
| `name`, `bio`, `profileImage` | `companyName`, `businessField`, `website` | `skills`, `activityCategory`, `experienceYears`, `hourlyRate`, `portfolioUrl` |

- 다른 역할의 필드를 보내면 거절하지 않고 **조용히 무시한다.** 화면이 역할과 상관없이 같은 폼을 보낼 수 있게 한 의도된 동작이다.
- 보낸 필드만 바뀐다. 숫자 필드는 `experienceYears`가 0 이상 정수, `hourlyRate`가 1원 이상 1억 원 이하의 원 단위
  정수여야 한다(0원은 거절. 규칙 전에 저장된 0원은 단가를 수정할 때까지 그대로 둔다). 잘못된 값은
  거절하고 저장된 값을 건드리지 않는다. 오타 하나로 프로필이 미완성이 되어 지원이 막히면 안 되기 때문이다.
- 기술(`skills`)은 저장 전에 별칭 표(`SKILL_ALIASES`, `src/lib/skills.ts`)로 정규화하고 중복을 없앤다. 예를 들어
  `PostgreSQL`은 `SQL`로 저장된다. 프로젝트의 요구 기술, 포트폴리오 기술, 검색과 추천도 같은 정규화를 쓴다.
- 프로필 이미지는 이미지 파일 하나, 5MB까지다.

### 공개 프로필

누구나 볼 수 있는 프로필에는 **이메일이 절대 들어가지 않는다.** 받은 리뷰(최신순), 평균 평점(리뷰가 없으면 없음),
리뷰 수, 포트폴리오 목록, 경력 목록과 경력 합계가 함께 나온다. 탈퇴한 사용자는 없는 사용자와 같다.

### 프로필 완성도

프로필 완성 관문([README](README.md#프로필-완성))과 별개로, 화면에 보여주는 0~100 점수가 있다. 관문을 바꾸지 않는다.
그래서 시급만 빠진 프리랜서는 90%인데 미완성이고, 관문 필드 네 개만 채운 프리랜서는 45%인데 완성이다. 역할은
토큰이 아니라 저장된 행을 본다(`PROFILE_SCORE_RULES`, `src/lib/profileCompletion.ts`).

| 프리랜서 항목 | 점수 | 의뢰인 항목 | 점수 |
| --- | --- | --- | --- |
| 기술 1개 이상 | 15 | 회사명 | 25 |
| 활동 분야 | 10 | 업종 | 25 |
| 경력 연수(0 이상 정수) | 10 | 소개 | 15 |
| 시급(0 초과) | 10 | 프로필 이미지 | 15 |
| 소개 | 10 | 웹사이트 | 20 |
| 프로필 이미지 | 10 | | |
| 포트폴리오 1개 이상 / 3개 이상 | 15 / 5 | | |
| 경력 1개 이상 | 10 | | |
| 지급 계좌 등록 | 5 | | |

## 포트폴리오

프리랜서가 한 작업을 보여주는 항목이다. 프리랜서만 만들고 고친다. 목록은 공개이고 로그인 없이 본다.

| 정책 | 값 (기준: `PORTFOLIO_LIMITS`, `src/schemas/profile.ts`) |
| --- | --- |
| 사용자당 항목 수 | 최대 20 |
| 제목 / 설명 / 맡은 역할 | 1~100자 / 2,000자 이하 / 100자 이하 |
| 링크 | `http`/`https` 절대 URL, 2,000자 이하 |
| 기술 | 정규화·중복 제거 후 최대 10개, 각 50자 이하 |
| 이미지 | 한 장, 5MB, 이미지 파일만 |
| 기간 | 시작·종료 연-월(`YYYY-MM`, KST). 미래 달 불가, 종료가 시작보다 앞설 수 없고, 종료만 있을 수 없다 |

- 정렬은 사용자가 정한 순서(`sortOrder`)가 먼저다. 새 항목은 맨 뒤에 붙는다. 순서 바꾸기는 자기 항목 **전부를
  정확히 한 번씩** 나열해야 한다. 일부만 보내거나 남의 항목을 섞을 수 없다.
- 항목 삭제는 하드 삭제이고 다른 항목의 순서 번호는 그대로 둔다(빈 번호는 괜찮다). 바꾸거나 지운 이미지 파일은
  저장소에서 지우지 않는다.
- 동시에 두 개를 추가해도 20개를 넘지 않는다. 생성·삭제·순서 변경은 사용자 행 잠금으로 직렬화된다.

## 경력

| 정책 | 값 (기준: `CAREER_LIMITS`, `src/schemas/profile.ts`) |
| --- | --- |
| 사용자당 항목 수 | 최대 30 |
| 회사 / 직책 | 각 1~100자 |
| 고용 형태 | `FULL_TIME`, `CONTRACT`, `FREELANCE`, `INTERN` |
| 기간 | 시작 연-월 필수, 종료 연-월이 없으면 재직 중. 재직 중인 항목이 여럿일 수 있다 |

- 정렬: 시작이 늦은 것 먼저, 같으면 재직 중인 것 먼저, 그다음 종료가 늦은 것.
- **경력 합계**(`careerSummary`)는 각 항목의 시작 달부터 종료 달(재직 중이면 이번 달)까지를 양 끝 포함해 세고,
  겹치거나 맞닿은 기간은 합쳐 한 달을 한 번만 센다. 예: `2020-01~2021-06`과 `2021-03~2022-02`는 합쳐 26개월,
  2년 2개월이다. 화면 표시용이고 프로필의 `experienceYears`를 바꾸지 않는다.
