# WorkBridge — Intended Behavior (Backend API)

## Purpose and how to read this

This document states what the API **should** do. It is the oracle for the test suite: tests
assert against this, not against the current implementation.

That distinction matters. A test generated by reading the code will faithfully encode whatever
the code does today, including its bugs. Everything below is written as intended behavior, and
where the current implementation disagrees it is marked **[D*n*]** and listed in
[Known divergences](#known-divergences). Those are expected to fail until fixed — that is the
point of writing them.

Where intent is genuinely undecided, it is marked **[Q*n*]** and listed in
[Open questions](#open-questions). Those need a product decision before a test can be written.

Sections written for the platform expansion give every rule a **stable identifier** at the start
of its bullet: **M** money and milestone rules, **CT** contracts, **PY** payments, **MS**
milestones, **S** settlements, **PA** payout account, **J** job handlers (`M3`, `MS14`, …). A
test that pins a rule carries the identifier in brackets in its name — `it('… [MS14]')` — the
same way D/Q/C tags are used. Identifiers are never renumbered; a withdrawn rule leaves a gap.
Later sections add **MG** conversations and messages, **PF** portfolio, careers and profile
completion, and **RC** recommendations, whose job handler continues the **J** series (`J8`), and
**NC** notification channels (preferences and email), whose email handler is `J9`.

Scope: the `workbridge-server` HTTP API. The Next.js client is out of scope. Written in English
(unlike the rest of `docs/`) because it is consumed as a test specification.

## Cross-cutting rules

These apply to every endpoint and deserve their own tests, since a violation anywhere is a bug.

### 1. Error envelope and error logging
Every error response body is exactly `{ "error": { "message": string } }`. Controllers signal
errors by throwing `AppError(message, statusCode)`; the terminal `errorHandler` renders it. No
controller writes an error response directly. **Only status 500 is logged at error level** —
exactly once per request, by `errorHandler` — and a 4xx never produces an error-level line.
Every request additionally produces one info-level access-log line whatever its status
(rule 9). **[C7]**

A request whose `Origin` is not allowed (`CLIENT_URL`, `CORS_ORIGINS`, plus
`http://localhost:3000` outside production) is **not an error**: it is answered normally but
without CORS headers, so the browser keeps the response from the page. It is never a 500 and
never logged at error level.

### 2. Authentication
- A Bearer access token in `Authorization` is required for every protected route.
- Missing header, malformed header (not `Bearer <token>`), expired token, or a token signed with
  the wrong secret → **401** `Invalid or expired token` (or `Authentication required` when the
  header is absent).
- Access tokens expire in 15 minutes. Refresh tokens live 7 days in an `httpOnly` cookie and are
  exchanged at `POST /api/auth/refresh`.
- The token payload is exactly `{ id, email, role }`. Access and refresh tokens carry the same
  shape.

### 3. Authorization
Two distinct layers, both required:
- **Role gating** — 403. Two mechanisms with **different messages**, which is worth knowing before
  asserting on wording: routes gated by the `requireRole` middleware return
  `Insufficient permissions`, but `GET /api/users/me/{applications,bookmarks,projects}` are gated
  *inside their controllers* and return bespoke strings (`Only freelancers can view their
  bookmarks`, `Only clients can view their projects`, …). Tests therefore assert **403 plus the
  error envelope**, not the exact text. Whether to unify these is **Q14**.
- **Ownership** — a resource may only be read or mutated by its owner (or, for contracts, either
  party). Ownership failures → **403** `Not authorized`. **Ownership is checked after existence**,
  so a non-existent resource returns 404 rather than 403. Note this ordering guarantee covers
  *ownership* only — **body validation may still precede existence**, so
  `PATCH /api/projects/:projectId/applications/:appId` with an invalid `status` on a non-existent
  project returns 400, not 404 (**Q15**). On the expansion routes the order is fixed rather than
  incidental: validation always runs before existence (rule 12).

### 4. Profile completeness
`requireCompleteProfile` gates project creation and applying. A CLIENT needs `companyName` and
`businessField`; a FREELANCER needs non-empty `skills`, `activityCategory`, an integer
`experienceYears >= 0`, and a finite `hourlyRate > 0`. Incomplete → **403**
`프로필을 먼저 완성해주세요`.

### 5. Soft delete
`User` and `Project` are soft-deleted via `deletedAt`. **Every read and write must filter
`deletedAt: null`.** A soft-deleted project must be invisible to listing, fetching, applying,
and bookmarking. A soft-deleted user must not be able to authenticate and must not appear in
public profile lookups.

Expansion resources follow their contract's project:
- A contract whose project is soft-deleted is **404** on every expansion path that reaches it or
  its milestones — `/api/contracts/:id/milestones`, `/api/milestones/:id/…`, `POST /api/payments`
  and `/dev-complete` by `milestoneId`, and `POST /api/payments/confirm` by `orderId` (before
  anything is captured) — and is left out of `GET /api/contracts`. (The pre-existing
  `GET /api/contracts/:id` and `POST /:id/sign` still miss this: **D21**.)
- **Exception — automatic approval proceeds.** Money already captured for a milestone must not be
  frozen because the client deleted the project, so the auto-approval job approves regardless and
  completes the contract when due, without writing the deleted project row or notifying anyone
  about that approval (MS17, J2). Manual approval of such a milestone stays 404.
- **Settlements and payout accounts are exempt.** They stay readable and keep being paid after a
  project is deleted: one settlement bundles items from several contracts, and the project of a
  completed contract may legitimately be deleted (S2).
- Expansion routes also re-check the *caller* (`requireActiveUser`, rule 12).
- Notifications created by expansion code are **never addressed to a soft-deleted user**. The state
  change still happens; only that user's notification is skipped.
- Conversations follow their contract's project the same way: 404 on every route, left out of
  lists and unread totals (MG10). Portfolio items and career entries follow their owner: they are
  invisible while the owner is soft-deleted and are themselves hard-deleted, never soft (PF20).
- Email is never addressed to a soft-deleted user: `notify()` creates no delivery for one, and a
  delivery whose recipient is soft-deleted before it is sent ends `SKIPPED` (NC10, J9).

### 6. Atomicity
Any operation that changes more than one row must be a single `prisma.$transaction`. If any step
fails, none may persist. This applies to accepting (including the default milestone) and rejecting
an application, closing recruitment, signing a contract (including its activation
notifications), replacing a milestone plan, confirming or dev-completing a payment (payment,
milestone funding, notification, jobs), submitting, approving (milestone, submission decision,
settlement item, notifications, contract and project completion) and rejecting a milestone, each
freelancer's share of the weekly settlement batch, each settlement state change, registering a
payout account (including the rescheduling of held settlements), and the lazy lifecycle sweep.
Notifications and jobs caused by a change are written in that change's transaction (rule 11).
Messaging and portfolios add: accepting also creates the conversation (MG3); every system message is written in
the transaction of the event it records (MG6); sending a message (message, attachments, digest
job, MG15); and creating a portfolio item or career entry or reordering the portfolio (PF8).
Notification channels add: every `notify()` call writes its in-app row, its email delivery and that delivery's
`notification.email` job in the caller's transaction (NC9); and updating notification
preferences (NC7).

### 7. Project lifecycle: lazy sweep on read paths and a scheduled sweep
`closeExpiredOpenProjects(now)` runs on read paths and:
- promotes `UPCOMING` → `OPEN` once `recruitmentStartDate <= now` and `deadline >= now`
- moves `UPCOMING`/`OPEN` → `CLOSED` once `deadline < now`
- rejects still-`PENDING` applications on projects that are now `CLOSED`

Consequence worth asserting explicitly: **`GET /api/projects` and `GET /api/projects/:id` write
rows.** They are not read-only.

In addition, **when a job runner is active** (the development worker, `npm run jobs:run`, or
`POST /api/internal/jobs/run`), the recurring job `project.lifecycleSweep` runs the same sweep
every 10 minutes (see [Background jobs](#background-jobs)). The sweep is idempotent, so the lazy
and the scheduled sweep may run in any order or concurrently and leave the same state. The
scheduled sweep only keeps statuses current when nobody is reading; production has no resident
worker, so the lazy sweep on read paths remains the guarantee. **[C6]**

### 8. Validation and status codes
- Missing required field → **400**
- Malformed value (unparseable number, invalid date, out-of-range enum) → **400**, never 500 **[D3]**
- Unique-constraint collision → **409**, never 500
- Upstream provider failure (OpenAI, TossPayments) → **502** or **400**, never 500

### 9. Request IDs and logging
- **Every response carries an `X-Request-Id` header** — successes, errors, `/health`, and
  unmatched paths alike. An incoming `X-Request-Id` that matches `^[A-Za-z0-9._-]{1,128}$` is
  echoed back unchanged; anything else (absent, empty, longer than 128, other characters) is
  replaced by a freshly generated UUID v4.
- The request id **never appears in a response body**. The error envelope stays exactly rule 1.
- Logs are single-line JSON objects `{ time, level, msg, requestId?, jobId?, ...fields }`.
  Levels are `debug < info < warn < error`; `LOG_LEVEL` (`debug|info|warn|error|silent`, default
  `info`) is the threshold. `error` lines go to stderr (`console.error`), the rest to stdout
  (`console.log`).
- **Access log:** one `info` line per request when the response finishes, with `method`, `path`
  (query string removed), `status`, `durationMs`, `ip` (rule 10's client IP) and `userId` when the
  request was authenticated. A 500 is access-logged at `info` like any other status.
- **Error level is reserved.** For a request's own outcome only `errorHandler` logs at `error`,
  and only for a 500 (rule 1). The queue also logs at `error`: when a job ends `FAILED` (in the
  handler or in stale-lock recovery), when a job's bookkeeping write fails, and when a worker
  poll fails. Those lines can appear during a request that still answers 200 — a job failing
  inside `POST /api/internal/jobs/run` — and they carry the job's `jobId`, not the request's
  outcome. The one pre-existing exception is `GET /api/auth/google/callback`, which logs the
  failure it swallows into a redirect.
- An `Error` placed in a log field is serialized explicitly as
  `{ name, message, stack, code?, statusCode?, meta? }` — never as `{}`.
- A job enqueued while serving a request records that request's id as its `traceId`; lines
  logged while a job runs — by its handler or by the runner about it — carry its `jobId` and, as
  `requestId`, that `traceId`.
- **Email.** The log mail provider writes each email as one `info` line `mail.sent`
  (NC14), with the recipient address and the full text — which is why it is a development
  provider (Q24). An unsupported `MAIL_PROVIDER` is reported once per process, as a `warn` line
  at start (NC14). A send that will be retried leaves the queue's `warn` line, and a delivery that
  ends `FAILED` is reported only by the queue's `job failed` error line; the email handler logs
  nothing at error level itself.

### 10. Rate limiting
- A limited request → **429** with the standard envelope
  `{ "error": { "message": "Too many requests. Try again later." } }` and a `Retry-After`
  header: whole seconds (at least 1) until the window that refused it ends.
- Windows are **fixed**, aligned to KST (UTC+9) boundaries: a 15-minute window starts at :00,
  :15, :30 or :45, an hour window on the hour, a day window at 00:00 KST. Counters live in
  Postgres, so every server instance shares them.
- Each counted request increments its counter, and is refused when the incremented count exceeds
  the limit; a refused request still counts. Where several rules apply they are evaluated in
  the order listed, and a request refused by one rule is not counted by the rules after it.
- **Client IP** (`lib/clientIp.ts`), the first that applies:
  1. `X-Client-IP`, when `PROXY_SHARED_SECRET` is set and the request's `X-Proxy-Secret` equals it
     (constant-time) and the value is an IP address. This is how the Next.js proxy names the
     browser. Without the secret — unset, missing or wrong — `X-Client-IP` is ignored, so a caller
     cannot choose its own key.
  2. On Vercel (`VERCEL=1`), the first address of `X-Vercel-Forwarded-For`. Vercel's edge replaces
     whatever the caller sent with the address that connected to it: the browser for a direct
     call, the Next.js function for a proxied one.
  3. Express's `req.ip`. With `TRUST_PROXY` set it is the client address taken from
     `X-Forwarded-For` after discarding the trusted proxies; unset, it is the socket address and
     `X-Forwarded-For` is ignored. On Vercel the socket address is always `127.0.0.1`.
- Both Next.js proxies (the `/api/*` catch-all and the auth routes) forward `X-Forwarded-For`
  **exactly as Next received it**, forward `X-Request-Id`, and copy `X-Request-Id` and
  `Retry-After` back to the browser. On Vercel with `PROXY_SHARED_SECRET` set they also send the
  browser's address (the edge-rewritten `X-Vercel-Forwarded-For` Next received) as `X-Client-IP`,
  with the secret as `X-Proxy-Secret`. Off Vercel they cannot name the browser: self-hosted Next
  does not expose its address to route handlers, and fills `X-Forwarded-For` with the socket
  address only when the client sent none. Consequences:
  - With `TRUST_PROXY=loopback`, a client that can reach a self-hosted Next directly chooses its
    own rate-limit IP by sending `X-Forwarded-For`. That setting is safe only while the Next
    port is reachable solely by trusted clients. **[Q23]**
  - Locally, the browser, Next and scripts all connect over loopback, so every local login
    without its own `X-Forwarded-For` is counted under one address (`::1`): the whole machine
    shares 20 logins per 15 minutes. Local tooling that drives many logins sets
    `RATE_LIMIT_ENABLED=false`.
- `RATE_LIMIT_ENABLED=false` disables every limit; the value is read per request. Default on.

  | Rule | Key | Window | Limit | What counts |
  |---|---|---|---|---|
  | login per IP | client IP | 15 min | 20 | every `POST /api/auth/login`, whatever its outcome (400 and 429 included) |
  | login failures | `email.trim().toLowerCase()` + client IP | 15 min | 5 | only `401 Invalid credentials` outcomes; a successful login resets it |
  | analyze per hour | user id | 1 hour | 5 | every `POST /api/projects/:id/analyze` that passes authentication and the `CLIENT` role check, whatever its outcome (404, 403, 502 included) |
  | analyze per day | user id | KST day | 20 | as above |

### 11. Background jobs and time
- Work that must happen later (or retried) is a `Job` row, **enqueued in the same transaction as
  the state change that causes it**, so a rolled-back change never leaves a job behind.
- A job may carry a `dedupeKey`. Enqueueing a key that already exists — in any status — is a
  silent no-op, never an error, so it is safe inside a transaction.
- Handlers are **idempotent**: they re-read state when they run and write conditionally, so
  running one twice (for example after stale-lock recovery) changes nothing the second time.
- Time-dependent services and handlers take `now` as an argument. Tests drive the queue with
  `runDueJobs({ now })` and never use fake timers.
- Calendar rules ("today", day windows, daily schedules) use **KST, a fixed UTC+9 offset** with no
  daylight saving.
- Job states, runners and the job types are specified in [Background jobs](#background-jobs).

### 12. Conventions of the expansion domains
These apply to the routes added by the platform expansion — everything documented after the
Notifications section, plus `GET /api/contracts`. Pre-existing endpoints keep the behavior documented for them, including
Q12/Q13; the mix is intended.
- Every new user-facing route runs `authenticate → requireActiveUser → [requireRole] → validate →
  controller`. `requireActiveUser` re-reads the caller and answers **401**
  `Account is no longer active` when the user is soft-deleted, so D12 does not exist on new
  routes. (Internal endpoints authenticate differently, see [Internal endpoints](#internal-endpoints--apiinternal).)
- Request validation failures → **400** with the message `<path>: <message>` for the **first**
  failing field, where `<path>` is the dotted field path (`items.0.amount`); a failure with no
  path is just `<message>`. Validation runs after authentication and role checks.
- Query parameters: an **empty value is absent** (`?limit=` → the default). A repeated
  parameter (`?limit=1&limit=2`), a fractional number where an integer is expected (`1.5`), and
  trailing garbage (`2abc`) → **400**.
- Money amounts in the new domains are whole won (integers); a non-integer amount → **400**.
- File uploads use one of two policies, and neither can surface as a 500 (no D6):

  | Upload | Field | Files | Size | Allowed types |
  |---|---|---|---|---|
  | attachment | `files` | 0–5 | 10 MB each | `image/*`, PDF, ZIP, plain text, Word/Excel/PowerPoint (legacy and OOXML), HWP |
  | image | `image` | 0–1 | 5 MB | `image/*` |

  Oversized file → **413**; disallowed type, too many files, an unexpected field name, or a
  malformed multipart body → **400**.
- Stored file keys are `<folder>/<uuid>.<ext>`, ASCII only; the original file name never appears
  in a key. The display name kept in the database is the original name restored from multer's
  latin1 decoding to UTF-8, so Korean names round-trip.

## Auth — `/api/auth`

### `POST /signup` — public
- Requires `email`, `password`, `name`, `role`; any missing → 400 `All fields are required`.
- `role` must be `CLIENT` or `FREELANCER` → else 400.
- Duplicate email → **409** `Email already in use`.
- On success: password is stored **bcrypt-hashed, never in plaintext**; responds **201** with
  `{ accessToken, user: { id, email, name, role } }` and sets the `refreshToken` cookie.
- The response must never include the password hash.

### `POST /login` — public
- Requires `email` and `password` → else 400.
- Unknown email, or a user with no password (OAuth-only account), or a wrong password → **401**
  `Invalid credentials`. All three must be indistinguishable, so the endpoint cannot be used to
  enumerate accounts.
- A soft-deleted user must not be able to log in.
- On success: **200** with `{ accessToken, user }` and a refreshed cookie.
- **Rate limited** (rule 10), checked before anything else, including the required-field check:
  - more than 20 requests from one client IP in a 15-minute window → **429**, whatever the
    outcome of the earlier ones;
  - after 5 `401 Invalid credentials` outcomes for one email (trimmed, lowercased) from one IP in
    a 15-minute window, further attempts for that email and IP → **429**, even with the correct
    password, until the window ends. Unknown emails count exactly like known ones, so the
    limiter cannot be used to enumerate accounts. A successful login clears the count. **[C8]**

### `POST /logout` — authenticated
- Clears the `refreshToken` cookie and returns 200.
- Tokens are stateless by design, so an already-issued access token remains valid until it expires
  (up to 15 minutes). Logout is effectively client-side only. The client also drops `accessToken`
  and `user` from `localStorage`.

### `POST /refresh` — public (relies on the cookie)
- No cookie → **401** `Refresh token not found`.
- Invalid/expired/wrong-secret token → **401** `Invalid or expired refresh token`.
- Token valid but the user no longer exists → **401** `User not found`.
- A soft-deleted user must not be able to refresh.
- On success: **200** with a new `{ accessToken }`. The refresh token is **not** rotated — by design.

### `GET /google` — public
- Redirects (**302**) to Google's consent screen with `client_id`, `redirect_uri`,
  `response_type=code`, `scope=openid email profile`, `access_type=offline` and `state`.
- `state` is fresh and random on every call (at least 32 characters) and is also set as the
  `oauthState` cookie: `httpOnly`, `SameSite=Lax`, `Secure` in production, path
  `/api/auth/google`, 10 minutes. The Next.js proxy moves it onto the browser's origin, and on the
  callback sends it back (login CSRF defence).
- If Google environment variables are missing, this must return a **500** error response and
  leave the process running — it must never crash the server.

### `GET /google/callback` — public
- Missing `code` → redirect to `${CLIENT_URL}/login?error=oauth_failed`.
- `state` missing, no `oauthState` cookie, or the two not equal (constant-time) → redirect to
  `${CLIENT_URL}/login?error=oauth_failed` **without exchanging the code**, so a callback URL
  carrying someone else's `code` cannot sign this browser in to their account.
- Every callback clears the `oauthState` cookie, whatever the outcome.
- Exchanges the code, fetches the profile, then links or creates:
  - existing account matched by `googleId` **or** `email` → attaches `googleId`, fills
    `profileImage` if empty, and flags `needsRoleSelection` from `roleSelected`
  - no match → creates a user with `role: 'FREELANCER'`, `roleSelected: false`, and
    `needsRoleSelection: true`
- Matching an existing password account **by email alone** links a Google identity without
  proving control of that address. **[D5]**
- Any failure must degrade to `${CLIENT_URL}/login?error=oauth_failed`, never a 500 or a crash.
- On success: redirects to `${CLIENT_URL}/auth/callback?token=…&needsRoleSelection=…` and sets
  the refresh cookie.

### `POST /select-role` — authenticated
- `role` must be `CLIENT` or `FREELANCER` → else 400.
- User not found → 404.
- Already chosen (`roleSelected === true`) → **400** `Role has already been selected`. This is
  one-way and must not be reusable to switch roles later.
- On success: sets the role, marks `roleSelected`, and **re-issues both tokens** so the new role
  is reflected in the claims.

## Users — `/api/users`

### `GET /me` — authenticated
Returns the caller's own profile including private fields (`email`). 404 if the record is gone.

### `PATCH /me` — authenticated, `multipart/form-data`
- `name`, `bio` and an optional `profileImage` file apply to both roles.
- **Role-scoped fields:** a CLIENT may set `companyName`, `businessField`, `website`; a
  FREELANCER may set `skills`, `activityCategory`, `experienceYears`, `hourlyRate`,
  `portfolioUrl`. Fields belonging to the other role are **silently ignored**, not rejected — this
  is intentional.
- `skills` is normalized through `SKILL_ALIASES` and de-duplicated before storage.
- `experienceYears` must be a non-negative integer (`0` or more — the same range
  `requireCompleteProfile` accepts, rule 4) and `hourlyRate` a finite number; non-numeric,
  fractional or negative `experienceYears` and non-numeric `hourlyRate` → **400**, row unchanged,
  not a 500 from the database. **[D3]**
- Uploads: images only, 5 MB max. Oversized → **413** (or 400); wrong MIME type → **400**. Neither
  may surface as 500. **[D6]**
- Only fields present in the request body are modified; omitted fields are untouched.

### `GET /:id` — public
- Returns the public profile only — **never `email`**.
- Includes `receivedReviews` (newest first), plus computed `avgRating` (`null` when there are no
  reviews) and `reviewCount`.
- Also includes `portfolioItems`, `careers` and `careerSummary`, exactly as the public portfolio
  and career routes return them (PF18). **[C10]**
- Unknown id → 404. A soft-deleted user must also 404.

### `GET /me/applications` — authenticated, FREELANCER only
- Non-freelancer → **403**. Runs the lifecycle sweep and rejects the caller's stale pending
  applications first, so returned statuses are current.
- Returns the caller's applications, newest first, with the linked project and contract.

### `GET /me/bookmarks` — authenticated, FREELANCER only
- Non-freelancer → **403**. Excludes bookmarks whose project is soft-deleted.
- Each entry is the project object plus `isBookmarked: true` and `bookmarkedAt`.

### `GET /me/projects` — authenticated, CLIENT only
- Non-client → **403**. Runs the lifecycle sweep first. Returns the caller's non-deleted
  projects, newest first, each with an application count.

## Projects — `/api/projects`

### `GET /` — public
- Runs the lifecycle sweep, then filters and paginates.
- Filters: `search` (case-insensitive, title **or** description), `category`, `minBudget`,
  `maxBudget`, `skills` (expanded through aliases, matches if *any* overlap), `status`.
- `status` defaults to **`OPEN`** and accepts `ALL | UPCOMING | OPEN | CLOSED`; anything else → 400.
  Note the default hides `UPCOMING` and `CLOSED` projects.
- `sort` defaults to `latest` and accepts `latest | deadline | budget`; anything else → 400.
  `latest` = `createdAt desc`, `deadline` = `deadline asc`, `budget` = `budget desc`.
- `page` defaults to 1, `limit` to 10 and is **capped at 50**. Non-positive or non-integer → 400.
- `minBudget > maxBudget` → 400.
- Soft-deleted projects never appear.
- Repeated query parameters (`?page=1&page=2`) fall back to the documented default rather than
  erroring.
- Response: `{ projects: [...], meta: { total, page, limit, totalPages } }`.

### `POST /` — authenticated, CLIENT, complete profile
- Requires `title`, `description`, `category`, `budget`, `deadline` → else 400.
- `deadline` must parse as a date; `budget` must be a non-negative number → else 400.
- `recruitmentStartDate` defaults to now, and must not be after `deadline` → else 400.
- A date-only value (`YYYY-MM-DD`, what the project form sends) is a **KST calendar day**: a
  `deadline` lasts until 23:59:59.999 KST of that day, a `recruitmentStartDate` begins at
  00:00 KST. So a project due today stays `OPEN` until the day ends, and one starting today is
  `OPEN` at once. A date-only value that is not a calendar date → 400. Any other value is read as
  an instant.
- Initial status is derived: `UPCOMING` if recruitment starts in the future, otherwise `OPEN`.
- `requiredSkills` is normalized and de-duplicated; omitting it yields `[]`.
- **201** with the created project. `clientId` is taken from the token, never from the body.

### `GET /:id` — public
Runs the lifecycle sweep, then returns the project with its client, application count, and
`pricingAnalysis`. Unknown or soft-deleted → 404.

### `PATCH /:id` — authenticated, CLIENT
- 404 if missing/deleted; 403 if not the owner.
- `title`, `description`, `category`, `requiredSkills` are always editable.
- **Once any application exists**, `budget`, `recruitmentStartDate`, and `deadline` are frozen —
  attempting to change any of them → **400**. This protects freelancers who applied against terms
  changing underneath them.
- With no applications, date changes are re-validated (`recruitmentStartDate <= deadline`) and,
  if the project is still `UPCOMING`/`OPEN`, its status is recomputed from the new schedule.
  Date-only values are KST days, as in `POST /`.
- Editing is permitted in any status, including `COMPLETED` and `CANCELLED` — intentional.

### `DELETE /:id` — authenticated, CLIENT
- 404 if missing/deleted; 403 if not the owner.
- **Refused with 409 if the project has a contract that is not `COMPLETED`** (i.e. `PENDING` or
  `ACTIVE`) — a project with work underway or awaiting signatures cannot be deleted out from under
  its counterparty. A project whose contract is `COMPLETED` may be deleted. **[D11]**
- **Soft** delete — sets `deletedAt`, never removes the row. Responds 200 with a message.

### `PATCH /:id/status` — authenticated, CLIENT
- 404 if missing/deleted; 403 if not the owner.
- Allowed transitions only, else **400** `Cannot transition from X to Y`:

  | From | To |
  |---|---|
  | `UPCOMING` | `OPEN`, `CANCELLED`, `CLOSED` |
  | `OPEN` | `CANCELLED`, `CLOSED` |
  | `IN_PROGRESS` | `COMPLETED`, `CANCELLED` |
  | `COMPLETED`, `CANCELLED`, `CLOSED` | *(terminal — no manual transitions)* |

- Transitioning to `CLOSED` must, **in one transaction**: update the project, reject all
  still-`PENDING` applications, and notify every distinct applicant once
  (`PROJECT_STATUS_CHANGED`).
- `IN_PROGRESS` appears in the table but **nothing in the system ever assigns it**. **[Q5]**

### `POST /:id/analyze` — authenticated, CLIENT
- 404 if missing/deleted; 403 if not the owner.
- Calls OpenAI `gpt-4o-mini` with `response_format: json_object`, deliberately **withholding the
  client's budget** so the estimate is independent of it.
- Model output is untrusted and must be normalized: each feature coerced to
  `{ name, description, estimatedCost, rationale, duration }`, features with
  `estimatedCost <= 0` dropped, and `totalAmount` **recomputed as the sum of the surviving
  features** rather than taken from the model.
- `summary` is model prose and its arithmetic is not trusted either: its sentences that state a
  won amount (`11,000,000원`, `1100만 원`, …) are dropped, so it cannot contradict the
  recomputed `totalAmount`; nothing left → `null`. `marketReference` is stored as written.
- Empty response → **502** `AI analysis did not return a response`. No usable features → **502**
  `AI analysis did not return valid feature pricing`. Neither may be a 500.
- Result is **upserted**, so re-analyzing replaces the previous analysis rather than duplicating it.
- **Rate limited per user** (rule 10): at most 5 calls per hour and 20 per KST day. The limiter
  runs after authentication and the `CLIENT` role check but before the project lookup, so 404,
  ownership 403 and 502 outcomes all count — the provider cost is incurred per request. The 6th
  call in an hour → **429** with `Retry-After`. **[C8]**

### Bookmarks — `/:id/bookmark`, authenticated, FREELANCER
- `GET` → `{ bookmarked: boolean }`.
- `POST` → **201** `{ bookmarked: true }`, idempotent (upsert), 404 if the project is missing or
  deleted.
- `DELETE` → 200 `{ bookmarked: false }`, idempotent (deleting a non-existent bookmark succeeds).
- `GET` and `DELETE` must treat a soft-deleted project as absent (rule 5), as `POST` does; today
  they do not check. **[D19]**
- Whether `GET` and `DELETE` should 404 for a project id that never existed, as `POST` does, is
  undecided. **[Q6]**

## Applications — nested under `/api/projects`

### `POST /:id/applications` — authenticated, FREELANCER, complete profile
- Runs the lifecycle sweep first.
- Requires `coverLetter`, `expectedRate`, `expectedDuration` → else 400.
- `expectedRate` must parse as a number `> 0` → else 400 `expectedRate must be a positive number`;
  a positive value below 1 → **400** `expectedRate must be at least 1`. A rate that rounds to
  0 won would create a contract whose milestone can never be paid (M7). **[C2]**
- Project missing/deleted → 404.
- If the project is `OPEN` but its deadline has already passed, it is closed (and its pending
  applications rejected) **in one transaction**, then → **400** `Project deadline has passed`.
- Project not `OPEN` → **400** `Project is not accepting applications`.
- Applying twice to the same project → **409** `You have already applied to this project`
  (enforced by the unique `(projectId, freelancerId)` constraint).
- On success, **in one transaction**: create the application as `PENDING` **and** notify the
  project's client (`APPLICATION_CREATED`). Responds **201**.

### `GET /:id/applications` — authenticated, CLIENT
- Project missing/deleted → 404; not the owner → 403.
- Rejects stale pending applications first, so returned statuses are current.
- Returns applications newest first with the freelancer's public profile, linked contract, and
  the project budget.
- Unpaginated. **[Q7]**

### `PATCH /:projectId/applications/:appId` — authenticated, CLIENT
- `status` must be `ACCEPTED` or `REJECTED` → else 400.
- Project missing/deleted → 404; not the owner → 403; application not found on that project → 404.
- The application must still be `PENDING`. Accepting an already-accepted or already-rejected
  application must be refused with **409**, and a project may never have two contracts.
- **`ACCEPTED` performs all of this in one transaction:**
  1. mark this application `ACCEPTED`
  2. mark every other `PENDING` application on the project `REJECTED`
  3. create a `Contract` (`status: PENDING`, `amount` = the application's `expectedRate`,
     `startDate` = now, `endDate` = the default milestone's due date — 30 days out, M9 —
     rather than the project's recruitment deadline, which may already have passed) **[C2]**
  4. create the contract's **default milestone** (M9): sequence 1, title `전체 작업`, amount
     `Math.round(contract.amount)`, due 30 days after the KST acceptance date, `PENDING` **[C2]**
  5. set the project to `CLOSED`
  6. notify the accepted freelancer (`APPLICATION_ACCEPTED`) and each rejected one
     (`APPLICATION_REJECTED`)
  7. create the contract's **conversation** with the client and the freelancer as its two
     participants, and post the `CONTRACT_CREATED` system message in it (MG3, MG7) **[C2]**

  If any step fails, none may persist — a failure creating the milestone leaves no contract.
  Responds `{ application, contract }` (the contract row, without milestones).
- **`REJECTED`**, in one transaction: mark the application `REJECTED` and notify the freelancer.
- The contract amount comes from the freelancer's `expectedRate`, **not** the project budget.
  It stays the stored value (possibly fractional); everything milestone-related uses it rounded
  to whole won (M7). The contract's `endDate` is the last milestone's due date: set at acceptance
  (step 3) and again whenever the plan is replaced (MS8).

## Contracts — `/api/contracts`

`GET /:id`, `POST /:id/sign` and `PATCH /:id` predate the expansion and keep their guard
(`authenticate` only — D12 and D21 still apply to them). `GET /` is an expansion route and runs
the rule 12 chain. The milestone-plan routes `GET`/`PUT /:id/milestones` are specified under
[Milestones](#milestones).

Contract status: `PENDING` (awaiting both signatures) → `ACTIVE` (both signed with a valid plan,
CT8) → `COMPLETED` (the last milestone was approved, MS17). There is no other transition, and no
endpoint completes a contract by hand.

### `GET /` — authenticated, either role
- **CT1** — Lists the contracts on which the caller is the client **or** the freelancer, newest
  first (`createdAt` desc). Contracts whose project is soft-deleted are left out (rule 5).
- **CT2** — Query: `status` optional, one of `PENDING | ACTIVE | COMPLETED`; `page` default 1,
  at most 1,000,000; `limit` default 20, **capped at 50** (a larger value yields 50). Anything
  else — unknown status, zero, negative, fractional, trailing garbage, repeated parameter, a page
  above 1,000,000 — → **400** (rule 12), never a 500.
- **CT3** — Response `{ contracts, meta: { total, page, limit, totalPages } }`. Each entry is
  `{ id, status, amount, startDate, endDate, completedAt, clientSigned, freelancerSigned,
  createdAt, myRole, project: { id, title, status }, counterpart: { id, name, profileImage },
  milestoneSummary }`, where `myRole` is `CLIENT` or `FREELANCER` (the caller's side of this
  contract) and `counterpart` is the other party — shown as stored even when that user is
  soft-deleted (whether joined users should be hidden is Q11). No email address appears
  (contrast Q9).

### `GET /:id` — authenticated
- **CT4** — Missing → 404 `Contract not found`; not a party → 403 `Not authorized`.
- **CT5** — Returns the contract with `project`, `client`, `freelancer`, `milestones` (sequence
  ascending, each a milestone object, MS1), `milestoneSummary`, and `reviews` (newest first).
  There is **no `payment` key**: payments belong to milestones. **[C4]**
- **CT6** — `milestoneSummary` is `{ count, contractAmount, fundedAmount, approvedAmount,
  approvedCount }`: `count` milestones in the plan; `contractAmount` the contract amount in whole
  won (M7) — the total a plan must add up to (M11), so a plan editor need not round `amount`
  itself; `fundedAmount` the sum of amounts of milestones that have been
  funded (status `FUNDED`, `SUBMITTED`, `REVISION_REQUESTED` or `APPROVED`); `approvedAmount` and
  `approvedCount` over `APPROVED` milestones only. The same object appears in `GET /` and
  `GET /:id/milestones`.

### `POST /:id/sign` — authenticated
- **CT7** — Check order: missing → 404 `Contract not found`; not a party → 403
  `Not authorized`; `COMPLETED` → **400** `A completed contract cannot be signed again`; then, for
  a `PENDING` contract only, an invalid milestone plan → **400**
  `Cannot sign a contract without a valid milestone plan`, and **no signature is recorded**.
  **[C5]**
  - A plan is valid when it has at least one milestone, every milestone is `PENDING`, and the
    amounts add up to `Math.round(contract.amount)` (M7, M11). Count limit, minimum amount and due
    dates are not re-checked here. The API cannot produce an invalid plan — acceptance creates a
    valid one and `PUT /:id/milestones` validates — so this guards against direct database edits.
  - An `ACTIVE` contract is not re-checked: re-signing it stays idempotent.
- **CT8** — Records the caller's signature — `clientSigned` for the client, `freelancerSigned`
  for the freelancer. Signing twice is idempotent. **When both signatures are present, the
  contract becomes `ACTIVE` exactly once**, and the same transaction notifies **each party once**
  with `CONTRACT_ACTIVATED`. **[C5]**
- **CT9** — Must be **atomic and concurrency-safe**: both parties signing simultaneously must
  still yield exactly one activation and exactly two `CONTRACT_ACTIVATED` notifications (one per
  party), never a contract stuck at `PENDING` with both flags set. A plan replacement racing a
  signature is serialized against it (MS9).
- **CT10** — A `COMPLETED` contract must **not** be signable back to `ACTIVE`.
- Returns the full contract, shaped as `GET /:id`.

### `PATCH /:id` — authenticated
- **CT11** — Always **410** `Contracts are completed automatically when every milestone is
  approved`, whatever the body, the id (existing or not) or the caller's relation to it; nothing
  is written. Without a token it is 401 like every protected route. The route is kept so that
  callers get the error envelope rather than Q10's HTML 404. Completion happens in the approval
  of the last milestone (MS17). **[C3]**

## Payments — `/api/payments`

All routes are authenticated; only the paying **client** may act on a payment. These routes
predate the expansion and keep their guard (`authenticate` only, hand-written validation — D12
applies, rule 12 does not).

**Payments are per milestone.** A contract has one payment per milestone (`Payment.milestoneId` is
unique; a contract has many payments), and a milestone is funded when its payment completes. The
client funds milestones one at a time, in sequence order (M13). **[C1]**

### `POST /` — create or resume a payment intent for a milestone
- **PY1** — Check order and messages:
  1. `milestoneId` missing → **400** `Milestone ID is required`. A `contractId` in the body is
     ignored — a body with only `contractId` is this 400.
  2. milestone missing, or its contract's project soft-deleted → **404** `Milestone not found`
  3. caller is not the contract's client (the freelancer included) → **403** `Not authorized`
  4. contract not `ACTIVE` → **400** `Contract must be active to proceed with payment`
  5. a milestone with a lower `sequence` on the same contract is still `PENDING` → **400**
     `Earlier milestones must be funded first` (M13)
  6. the milestone is not `PENDING` → **409** `Milestone is already funded`
  7. then by the milestone's existing payment, per PY2. **[C1]**
- **PY2** — Behavior by existing payment state:

  | Existing payment | Result |
  |---|---|
  | none | create `PENDING` with a fresh `orderId` → **201** |
  | `PENDING` | return the existing `orderId`/`amount` → **200** (resumable, no duplicate) |
  | `FAILED` | reset to `PENDING` with a **new** `orderId`, clear `paymentKey`, re-take `amount` from the milestone → **200** (retry) |
  | `REFUNDED` | **409** `Payment cannot be created for this milestone` |
  | `COMPLETED` | **409** `Payment already completed for this milestone` — reachable only when the milestone is `PENDING` but its payment is `COMPLETED`, an inconsistent state; normally step 6 answers first |

- **PY3** — `amount` is always the milestone's `amount`, never from the request body. The payment
  row records the milestone's `contractId`, the `milestoneId` and the caller as `clientId`.
- **PY4** — Response `{ orderId, amount, paymentId }`.
- A non-string `milestoneId` (e.g. a number) is a malformed value that rule 8 says should be 400;
  today it reaches Prisma and is a 500 (D14 covers the leaked message).

### `POST /confirm` — verify with TossPayments
- **PY5** — Check order: `paymentKey`, `orderId`, `amount` all required → else **400**
  `paymentKey, orderId, and amount are required`; `amount` must be a positive finite number → else
  **400** `Invalid payment amount`; payment not found, **or its milestone's contract's project
  soft-deleted** → **404** `Payment not found` (checked before the provider is contacted, so
  nothing is captured for a deleted project — the same condition as `/dev-complete`, rule 5); not
  the caller's → **403** `Not authorized` **[C1]**; payment not `PENDING` → **409**
  `Payment has already been processed` (this makes confirmation non-replayable, though not under
  concurrency — **D18**); submitted `amount` ≠ stored amount → **400**
  `Payment amount does not match the contract amount` (wording predates milestones; the stored
  amount is the milestone's). A client must not be able to pay less than the milestone value.
- Verifies against TossPayments and requires the provider to report `status === 'DONE'` **and** a
  matching `totalAmount`.
- **PY6** — On success, **in one transaction**: the payment becomes `COMPLETED` with its
  `paymentKey`, **and the milestone is funded** (PY7). Responds **200** with the updated payment
  row. **[C1]**
- **PY7** — *Funding a milestone* (shared with `/dev-complete`): a conditional `PENDING → FUNDED`
  write that sets `fundedAt`. When it transitions the milestone, the same transaction notifies the
  freelancer (`MILESTONE_FUNDED`) and enqueues `milestone.dueSoon` and `milestone.overdue` (J4,
  J5). When the milestone is **not** `PENDING` any more — a concurrent confirm already funded it
  (D18) — the step is a **no-op**: it does not throw, notifies nobody and enqueues nothing, and
  the payment still completes. (Throwing here would be caught by the verification catch-all below
  and would overwrite the winner's `COMPLETED` payment with `FAILED`.)
- **PY8** — On any verification failure the payment is marked **`FAILED`** and the response is
  **400** `Payment verification failed`. The `FAILED` write is **conditional on the payment still
  being `PENDING`** (`updateMany` where `orderId` and `status: PENDING`): a confirm that loses a
  race to a successful one — the real provider rejects the second confirmation of one payment —
  must never turn the winner's `COMPLETED` payment back into `FAILED`; it still answers 400. **If any database write after the provider has captured
  the payment fails (including notification or job enqueue), the payment is marked FAILED and the
  response is 400 — existing behaviour of the D8 family, not a new divergence.** The underlying
  cause must be logged — a network fault and a genuine amount mismatch currently produce identical
  output. **[D8]**
- **PY9** — Two simultaneous confirms of one `PENDING` payment, whatever D18 does to their status
  codes, must leave the payment `COMPLETED`, the milestone `FUNDED`, **exactly one**
  `MILESTONE_FUNDED` notification and one `milestone.dueSoon`/`milestone.overdue` job each — both
  when the provider accepts both calls (the no-op funding step, PY7) and when it **rejects the
  second** (the conditional `FAILED` write, PY8). These are required behavior, not a divergence.

### `POST /dev-complete` — local/demo shortcut
- **PY10** — Check order and messages:
  1. **403 `Payment bypass is disabled` unless `ALLOW_PAYMENT_BYPASS === 'true'`**, before
     anything else. This must be `false` in production, and the check must be evaluated per
     request so it cannot be bypassed by a stale module-load value.
  2. `milestoneId` missing → **400** `Milestone ID is required`
  3. milestone missing or its project soft-deleted → **404** `Milestone not found`
  4. not the contract's client → **403** `Not authorized`
  5. contract not `ACTIVE` → **400** `Contract must be active to proceed with payment`
  6. an earlier milestone is still `PENDING` → **400** `Earlier milestones must be funded first`
  7. the milestone is not `PENDING`: if its payment is `COMPLETED` → **200** with the payment
     unchanged (idempotent replay); otherwise → **409** `Milestone is already funded`
  8. its payment is `REFUNDED` → **409** `Payment cannot be completed for a refunded milestone`
     **[C1]**

  Steps 4–6 and the not-`PENDING` 409 match PY1, so the same state gets the same answer on both
  routes.
- **PY11** — Otherwise (the milestone is `PENDING`), **in one transaction**: the payment becomes
  `COMPLETED` with `paymentKey: dev_bypass_<milestoneId>` and `amount` = the milestone's amount —
  an existing `PENDING`, `FAILED` or (inconsistently) already-`COMPLETED` row is updated in place
  keeping its `orderId` (**200**), or a row is created with `orderId` `dev-<uuid>` (**201**) — and
  the milestone is funded exactly as PY7. So dev-complete also repairs a `PENDING` milestone whose
  payment is `COMPLETED`, which `POST /` can only refuse. TossPayments is never contacted. Responds
  with the payment row. Two concurrent calls on a milestone with no payment row must not 500
  (rule 8). **[C1]** **[D22]**

### `GET /` — authenticated
- **PY12** — The caller's payments (`clientId` = caller), newest first, each with its contract
  (with `project { id, title }` and `freelancer { id, name }`) and
  `milestone { id, sequence, title }`. Unpaginated. **[Q7]** **[C1]**

## Money and milestone rules

Every business constant of milestones and settlements is stated here once; other sections refer
to these identifiers. The pre-existing amount columns are `Float` and stay so; the expansion only
ever writes whole-won values into them, and all its arithmetic is on integers.

| ID | Rule |
|---|---|
| **M1** | **Platform fee:** 10% of the approved milestone amount (`feeRateBps = 1000`), borne by the freelancer. The client pays exactly the milestone amount. |
| **M2** | **VAT on the fee:** 10% of the fee, also borne by the freelancer. |
| **M3** | **Arithmetic:** `fee = floor(gross × feeRateBps / 10000)`, `vat = floor(fee × 1000 / 10000)`, `net = gross − fee − vat`, all in integers. Fractions of a won are **dropped** (floored), never rounded up. |
| **M4** | **Rate snapshot:** each settlement item stores the `feeRateBps` in force when its milestone was approved; a later rate change never alters existing items. |
| **M5** | **Settlement totals** are the sums of their items' stored `gross`/`fee`/`vat`/`net`, never recomputed from the total gross. |
| **M6** | **Whole won:** every amount the expansion accepts is an integer number of won; a non-integer → 400 (rule 12). |
| **M7** | **Contract amount in won** is `Math.round(contract.amount)` (half up). `contract.amount` comes from the application's `expectedRate`, which may be fractional. The default milestone (M9), the plan sum (M11) and the signing check (CT7) all use this value. Applying requires `expectedRate >= 1`, so this is always at least 1 won. The migration that backfills a default milestone for contracts created before the expansion uses `ROUND(amount::numeric)`, which rounds halves up like `Math.round` for positive values — Postgres `round()` on a `float8` rounds halves to even (`2500000.5` → 2500000) and would leave a backfilled plan one won short of CT7's check. |
| **M8** | **Milestone count:** 1 to 10 per contract. |
| **M9** | **Default milestone,** created when an application is accepted: sequence 1, title `전체 작업`, no description, amount = M7, due at the end of the KST day 30 days after the KST acceptance date (accepted 2026-10-21 14:00 KST → due 2026-11-20 23:59:59.999 KST). The contract's `endDate` is set to the same instant. It is exempt from M10. |
| **M10** | **Minimum milestone amount:** 10,000 won, for every milestone of a plan submitted with `PUT`. (A contract worth less than 10,000 won therefore keeps its default milestone.) |
| **M11** | **Plan sum:** the amounts of a plan add up to M7 exactly → else **400** `Milestone amounts must add up to the contract amount (N)`, where `N` is the M7 value as plain digits (`(1500000)`). |
| **M12** | **Due dates** are calendar dates `YYYY-MM-DD`, interpreted in KST. **Today (KST) is allowed**; an earlier date → 400. Within a plan they must not decrease with `sequence` (equal dates allowed). A due date is stored as the last millisecond of that KST day: `2026-11-02` → `2026-11-02T14:59:59.999Z`. |
| **M13** | **Sequential funding:** milestones are funded in `sequence` order. While any milestone with a lower sequence is `PENDING`, funding another → **400** `Earlier milestones must be funded first`. |
| **M14** | **Auto-approval:** a submission not approved or rejected within `MILESTONE_AUTO_APPROVE_DAYS` days is approved automatically. The env value is a positive integer number of days (unset or not a positive integer → **7**), counted as exact 24-hour periods: `autoApproveAt = submittedAt + days × 24 h` (168 h by default), not KST calendar days. Rejecting clears the timer; a resubmission starts a new one. |
| **M15** | **Auto-approval reminder:** at `autoApproveAt − 48 h` the client is reminded. If that instant is not in the future when the submission is made, no reminder is scheduled. |
| **M16** | **Due-date notices:** at `dueDate − 24 h` the freelancer gets `MILESTONE_DUE_SOON` (not scheduled if that instant has already passed when the milestone is funded), and at `dueDate` both parties get `MILESTONE_OVERDUE` — each only while the milestone is `FUNDED` or `REVISION_REQUESTED`. There is no late penalty, and a late submission is accepted. A milestone funded after its due date has already passed gets `MILESTONE_OVERDUE` on the next runner pass — intended: the parties should agree a new schedule. |
| **M17** | **Revisions:** unlimited. Each rejection increments `revisionCount`; nothing else depends on it. |
| **M18** | **Text limits** (measured as JavaScript string length after trimming): milestone `title` 1–100, `description` 0–2,000; submission `message` 1–5,000; at most 5 `links`, each an absolute `http`/`https` URL of at most 2,000 characters; at most 5 files under rule 12's attachment policy; rejection `reason` 10–2,000 (exactly 10 passes, 9 fails). |
| **M19** | **Settlement calendar (KST):** a settlement period runs from Monday 00:00 to the next Monday 00:00 (`periodEnd`, exclusive). The weekly batch runs at `periodEnd + 3 h` (**Monday 03:00**) and schedules the payout at `periodEnd + 2 days 10 h` (**Wednesday 10:00**). |
| **M20** | **Settlement eligibility:** a batch settles every item that is in no settlement yet and has `approvedAt < periodEnd`. An item therefore normally lands in the settlement of the week it was approved in; one that a batch missed (a late or failed run, or S5's non-`SCHEDULED` case) is caught up by the next batch, into that batch's period. |
| **M21** | **Minimum payout:** none. |
| **M22** | **Payout attempts:** at most **3** transfer attempts per settlement in total (the first plus two retries). A failed attempt is retried 24 hours later; an `ON_HOLD` rescheduling in between (PA4) can make the gap longer. |
| **M23** | **Payout account:** bank code from the fixed list below; account number with hyphens and spaces removed must be 10–14 digits; the account holder must be the member — `holderName` equals the user's `name` ignoring all whitespace and letter case. Responses show `accountNumberMasked` only: every digit but the last four replaced by `*` (`110123456789` → `********6789`). |

Worked fee example (M3), and why M5 sums items rather than recomputing:

| Gross | Fee (10%) | VAT on fee | Net |
|---|---|---|---|
| 1,234,567 | 123,456 | 12,345 | 1,098,766 |
| 9,500,000 | 950,000 | 95,000 | 8,455,000 |
| 10,000 | 1,000 | 100 | 8,900 |
| 15,005 | 1,500 | 150 | 13,355 |
| two items of 15,005 (a settlement) | 3,000 | 300 | 26,710 |

Recomputing the last row from its total gross of 30,010 would give a fee of 3,001; the settlement
reports 3,000, the sum of its items.

Worked calendar example (M19, M20): a milestone approved on Tuesday 2026-10-20 14:00 KST falls in
the period starting Monday 2026-10-19 00:00 KST (`2026-10-18T15:00:00.000Z`). The batch for it
runs on Monday 2026-10-26 03:00 KST (`2026-10-25T18:00:00.000Z`) and schedules the payout for
Wednesday 2026-10-28 10:00 KST (`2026-10-28T01:00:00.000Z`). A milestone approved at exactly
2026-10-26 00:00:00.000 KST belongs to the next period, even though that period's batch has not
run yet.

## Milestones

A contract's work is split into milestones. Each is funded by the client (Payments), delivered by
the freelancer through submissions, and approved or sent back by the client — or approved
automatically (M14). An approved milestone becomes a settlement item for the freelancer.

### Objects
- **MS1** — A **milestone object** is the milestone row — `id, contractId, sequence, title,
  description, amount, dueDate, status, fundedAt, submittedAt, autoApproveAt, approvedAt,
  approvalType, revisionCount, createdAt, updatedAt` — plus `payment` (its payment row, or
  `null`) and `latestSubmission` (the submission with the highest `round`, with its
  `attachments`, or `null`), plus `payoutPreview` — `{ gross, fee, vat, net }` for this
  milestone: its settlement item's stored values when it has one (M4), otherwise M3 at the
  current rate (including milestones approved before the expansion, which have no item, S3).
  `autoApproveAt` is non-null only while `SUBMITTED`. **[C4]**
- **MS2** — A **submission object** is `{ id, milestoneId, round, message, links, decision,
  decisionReason, decidedAt, decidedById, autoDecided, submittedAt, attachments }`, where
  `decision` is `null` while awaiting review, `APPROVED` or `REJECTED`; `decidedById` is `null`
  for an automatic approval (`autoDecided: true`); and each attachment is
  `{ id, url, fileName, mimeType, size, createdAt }` with `fileName` the original UTF-8 name.

### States
- **MS3** — Transitions:

  | From | To | Trigger | Actor |
  |---|---|---|---|
  | — | `PENDING` | application accepted (default milestone, M9) or plan replaced (MS8) | system / client |
  | `PENDING` | *(deleted)* | plan replaced while the contract is `PENDING` (MS8) | client |
  | `PENDING` | `FUNDED` | payment confirmed or dev-completed (PY7) | client |
  | `FUNDED` | `SUBMITTED` | first submission (round 1) | freelancer |
  | `REVISION_REQUESTED` | `SUBMITTED` | resubmission (round + 1) | freelancer |
  | `SUBMITTED` | `APPROVED` (`MANUAL`) | `POST /api/milestones/:id/approve` | client |
  | `SUBMITTED` | `REVISION_REQUESTED` | `POST /api/milestones/:id/reject` | client |
  | `SUBMITTED` | `APPROVED` (`AUTO`) | `milestone.autoApprove` job (J2) | system |

  `APPROVED` is terminal. There is no refund, dispute or cancellation path (Q5).
- **MS4** — Every transition is a **conditional write on the expected status**, so of two
  concurrent attempts exactly one wins. A transition requested by a user (submit, approve,
  reject, plan replacement) that loses — the status changed between its check and its write —
  is answered with the same **409** as if the check had failed, and writes nothing. The single
  exception is funding (`PENDING → FUNDED`), which is a silent no-op when it loses (PY7).

### Common to the routes below
- **MS5** — All are expansion routes (rule 12): `authenticate` → `requireActiveUser` → role (where
  stated) → validation → existence → ownership → state. Therefore a validation failure is a 400
  even for a non-existent id. A milestone that does not exist, or whose contract's project is
  soft-deleted, → **404** `Milestone not found`; a contract likewise → **404**
  `Contract not found`. A caller who is not the required party → **403** `Not authorized`; a
  caller with the wrong role → **403** `Insufficient permissions`. For a `type` error (wrong JSON
  type) the message after `<path>: ` is zod's default and tests assert only the prefix; the
  messages quoted below are exact.

### `GET /api/contracts/:id/milestones` — either party
- **MS6** — 404 / 403 per MS5 (either party may read). Responds **200**
  `{ milestones, milestoneSummary }` — milestone objects in `sequence` order and CT6's summary.

### `PUT /api/contracts/:id/milestones` — CLIENT, the contract's client
- **MS7** — Replaces the whole plan. Body `{ milestones: [{ title, description?, amount,
  dueDate }] }`; array order defines `sequence` 1..n. Check order and messages:
  1. validation → **400**:
     - `milestones` with fewer than 1 or more than 10 entries →
       `milestones: A contract must have between 1 and 10 milestones` (M8)
     - `milestones.<i>.title` empty after trimming → `…title: Title is required`; over 100 →
       `…title: Title must be at most 100 characters`; `description` over 2,000 →
       `…description: Description must be at most 2000 characters` (M18). An empty
       `description` is stored as `null`.
     - `milestones.<i>.amount` not an integer → `…amount: Amount must be a whole number of won`
       (M6); below 10,000 → `…amount: Amount must be at least 10000` (M10)
     - `milestones.<i>.dueDate` not a real `YYYY-MM-DD` date →
       `…dueDate: Due date must be a YYYY-MM-DD date`; before today in KST →
       `…dueDate: Due date cannot be in the past`; earlier than the previous entry's →
       `…dueDate: Due dates must not decrease` (M12)
     - the per-entry checks above are reported in array order (the first failing entry wins);
       the order check compares entries with each other, so it runs only after every entry
       passed its own checks
  2. contract missing or its project soft-deleted → **404** `Contract not found`
  3. caller is not the contract's client → **403** `Not authorized`
  4. contract not `PENDING` (`ACTIVE` or `COMPLETED`) → **409**
     `Milestone plan is locked once the contract is active`
  5. amounts do not add up → **400** `Milestone amounts must add up to the contract amount (N)`
     (M11)
- **MS8** — On success, **in one transaction**: the contract's signatures are both reset to
  `false` and its `endDate` becomes the last milestone's due date; every existing milestone is
  deleted (they are all `PENDING` while the contract is) and the new ones created `PENDING`; and,
  if at least one signature was present before the call, the freelancer is notified
  (`MILESTONE_PLAN_UPDATED`). Changed terms must be signed again by both parties.
- **MS9** — The transaction's **first statement locks the contract row and reads its
  pre-image** (`SELECT "status", "clientSigned", "freelancerSigned" FROM "Contract" WHERE id = $1
  FOR UPDATE`, raw SQL). If the locked status is not `PENDING` the request is the 409 of step 4.
  Only then are the signatures reset and `endDate` set, and MS8's "a signature was present" is
  decided from that **locked pre-image** — never from a read taken before the transaction, which
  would let a signature landing in between be wiped without a notification. A concurrent signature
  serializes on the same row lock: if it commits first and activates the contract, the
  replacement → 409 and the plan is unchanged; if the replacement commits first, the signature
  lands on the reset contract and the contract stays `PENDING` until the other party signs again.
- **MS10** — Responds **200** `{ contract: { id, status, amount, endDate, clientSigned,
  freelancerSigned }, milestones }` with the new milestone objects.

### `GET /api/milestones/:id` — either party
- **MS11** — 404 / 403 per MS5. Responds **200** with the milestone object (MS1, including
  `payoutPreview`) plus:
  - `submissions` — every submission object, `round` descending, with attachments;
  - `contract` — `{ id, status, amount, clientId, freelancerId, project: { id, title } }`.

### `POST /api/milestones/:id/submissions` — FREELANCER, the contract's freelancer
- **MS12** — `multipart/form-data` with `message`, zero or more `links` fields, and zero or more
  `files` (rule 12 attachment policy; its 413 / 400 come after the role check and before
  validation). A JSON body with `message` and `links` is accepted too when there are no files; a
  single `links` value is a one-element list. Check order and messages:
  1. validation → **400**: `message` empty after trimming → `message: Message is required`; over
     5,000 → `message: Message must be at most 5000 characters`; more than 5 links →
     `links: At most 5 links are allowed`; a link that is not an absolute `http`/`https` URL of at
     most 2,000 characters → `links.<i>: Links must be http or https URLs` (M18)
  2. **404** / **403** per MS5 (the caller must be the contract's freelancer)
  3. milestone not `FUNDED` or `REVISION_REQUESTED` → **409**
     `Milestone is not awaiting a submission` (the contract is necessarily `ACTIVE` then)
- **MS13** — Then the files are stored (keys `milestones/<milestoneId>/<uuid>.<ext>`; a storage
  failure → **502** and nothing is written), and **in one transaction**, in this order: **first**
  the conditional status write `FUNDED | REVISION_REQUESTED → SUBMITTED` with `submittedAt = now`
  and `autoApproveAt` per M14 — if it matches nothing, the request is the 409 of step 3; **then**
  the submission is created with `round` = highest existing round + 1 (1 for the first), computed
  only after that write holds the milestone's row lock, so two concurrent submissions never
  compute the same round (the loser is a 409, never a 500 from the `(milestoneId, round)` unique
  constraint); then `milestone.autoApprove` and (M15) `milestone.autoApproveReminder` are enqueued
  for that round (J2, J3) and the client is notified (`MILESTONE_SUBMITTED`). Files already stored
  by a request that ends in 409 are left in the bucket unreferenced.
- **MS14** — Responds **201** `{ milestone, submission }` (milestone object, submission object).
  A submission after the due date is accepted (M16).

### `POST /api/milestones/:id/approve` — CLIENT, the contract's client
- **MS15** — No body. **404** / **403** per MS5, then milestone not `SUBMITTED` → **409**
  `Milestone is not awaiting review`.
- **MS16** — **In one transaction**, in this order: **first** the contract row is locked
  (`SELECT … FROM "Contract" WHERE id = $1 FOR UPDATE`, raw SQL), so approvals of different
  milestones of one contract serialize (MS22); **then** the conditional write
  `SUBMITTED → APPROVED` — if it matches nothing, the request is the 409 of MS15 — setting
  `approvedAt = now`, `approvalType: MANUAL` and `autoApproveAt = null`; the latest submission gets
  `decision: APPROVED`, `decidedAt`, `decidedById` = the client; a **settlement item** is created
  for the freelancer (S3); the freelancer is notified (`MILESTONE_APPROVED`); and MS17 applies.
  Responds **200** `{ milestone, contract: { id, status, completedAt } }`.
- **MS17** — **Contract completion is automatic.** After the milestone write, a **fresh
  statement** counts the contract's milestones that are not `APPROVED`. When there are none —
  the approval, manual or automatic, approved the last one — the same transaction sets the
  contract `COMPLETED` with `completedAt = now`, sets the project `COMPLETED` (directly from
  `CLOSED`, bypassing `validTransitions` — **[Q5]**), and notifies both parties
  (`CONTRACT_COMPLETED`). Reviews become possible from then on. **[C3]**
  - When the contract's project is **soft-deleted** — reachable only through automatic approval
    (MS20), since the manual route is 404 — the contract still completes and the settlement item
    is still created, but the project row is **not written** and **no notification** of that
    approval is created (neither `MILESTONE_AUTO_APPROVED` nor `CONTRACT_COMPLETED`): the pages
    they would link to are gone. Money already captured is never frozen by a deletion (S2).

### `POST /api/milestones/:id/reject` — CLIENT, the contract's client
- **MS18** — Body `{ reason }`. Check order: `reason` shorter than 10 after trimming →
  **400** `reason: Reason must be at least 10 characters`, longer than 2,000 →
  **400** `reason: Reason must be at most 2000 characters` (M18); **404** / **403** per MS5;
  milestone not `SUBMITTED` → **409** `Milestone is not awaiting review`.
- **MS19** — **In one transaction**, **first** the conditional write `SUBMITTED →
  REVISION_REQUESTED` (no match → the 409 of MS18) with `revisionCount` +1 and
  `autoApproveAt = null`; then the latest submission (read after that write) gets `decision: REJECTED`,
  `decisionReason` (trimmed), `decidedAt`, `decidedById`; the freelancer is notified
  (`MILESTONE_REVISION_REQUESTED`). Pending jobs for the rejected round are left in place and
  turn into no-ops (J2, J3). Responds **200** `{ milestone }`.

### Automatic approval
- **MS20** — The `milestone.autoApprove` job (J2) approves exactly as MS16 — contract lock first,
  then the conditional milestone write — except: the conditional write also requires
  `autoApproveAt <= now`, so a job for an earlier round can never approve a later round's fresh
  submission; it proceeds **whether or not the project is soft-deleted** (MS17's deleted-project
  case); `approvalType: AUTO`; the submission gets `decision: APPROVED`, `decidedById: null`,
  `autoDecided: true`; and **both** parties are notified with `MILESTONE_AUTO_APPROVED` instead of
  `MILESTONE_APPROVED`. A soft-deleted party does not stop it — the money is not held hostage —
  only that party's notification is skipped (rule 5). MS17 applies.
- **MS21** — Manual and automatic approval racing on one milestone: exactly one wins (MS4).
  Afterwards there is exactly one settlement item, exactly one of `MILESTONE_APPROVED` /
  `MILESTONE_AUTO_APPROVED`, and at most one `CONTRACT_COMPLETED` per party. The losing request
  is the 409 of MS15; a losing job ends as a successful no-op.
- **MS22** — Approvals of **different** milestones of one contract racing each other — the last
  two approved at once, manually, automatically or one of each — serialize on the contract row
  lock (MS16), so the second to commit sees the first's approval in MS17's fresh count. When they
  are the last two, the contract ends `COMPLETED` with exactly one `CONTRACT_COMPLETED` per party;
  it can never be left `ACTIVE` with every milestone `APPROVED`.

## Settlements — `/api/settlements`

Approved milestone money reaches the freelancer through weekly settlements. A **settlement item**
is one approved milestone's `gross`/`fee`/`vat`/`net`; a **settlement** bundles one freelancer's
items for one period and is paid out once. Payouts go through a `PayoutProvider`; the default
provider only logs the transfer and succeeds — real bank transfers are out of scope.

- **S1** — Settlement states:

  | From | To | Trigger |
  |---|---|---|
  | — | `SCHEDULED` | the weekly batch creates it (S4); a payout is scheduled for `scheduledPayoutAt` |
  | `SCHEDULED` | `PROCESSING` | the payout runs and a payout account exists (S9); `payoutAttempts` +1 |
  | `SCHEDULED` | `ON_HOLD` | the payout runs and there is no payout account, or the freelancer is soft-deleted (S8); `payoutAttempts` unchanged |
  | `ON_HOLD` | `SCHEDULED` | the freelancer registers a payout account (PA4); rescheduled to the next Wednesday 10:00 KST |
  | `PROCESSING` | `PAID` | the transfer succeeds (S10) |
  | `PROCESSING` | `FAILED` | the transfer fails (S11); retried after 24 h while attempts remain (M22) |
  | `FAILED` | `PROCESSING` | the retry runs and a payout account exists (S9) |
  | `FAILED` | `ON_HOLD` | the retry runs and there is no payout account any more (S8) |

  `PAID` is terminal; so is `FAILED` once `payoutAttempts` is 3 — an operator handles it from
  there (out of scope).
- **S2** — Settlements ignore project soft-deletion entirely: items are batched, paid and shown
  (with `projectDeleted: true`) whether or not their project still exists (rule 5).
- **S3** — A settlement item is created **in the approval transaction** (MS16, MS20), one per
  milestone (`milestoneId` unique): `freelancerId`, `contractId`, `grossAmount` = the milestone
  amount, `feeRateBps` (M4), `feeAmount`, `feeVatAmount`, `netAmount` (M3), `approvedAt` = the
  milestone's, no settlement yet. Milestones approved before the expansion have no items.

### Weekly batch (`settlement.weeklyBatch`, J6)
- **S4** — Settles the period of the job's **slot**, which is read from its `dedupeKey`
  (`settlement.weeklyBatch:<periodStart>`): `periodStart` is that instant (a Monday 00:00 KST)
  and `periodEnd = periodStart + 7 days`. The period is **never derived from the job's current
  `runAt`** — a retry moves `runAt` to `now + backoff`, and the slot is the only stable record of
  which week the job is for. A late or retried batch therefore still settles its own week, and
  its `scheduledPayoutAt` (M19) may already be in the past, in which case the payout runs on the
  next runner pass. For every freelancer with eligible items (M20: unsettled,
  `approvedAt < periodEnd`), **in one transaction per freelancer**: create the freelancer's
  settlement for that `periodStart` as `SCHEDULED` with `periodStart`, `periodEnd`,
  `scheduledPayoutAt`; attach the eligible items; set `itemCount` and the totals (M5); notify the
  freelancer (`SETTLEMENT_SCHEDULED`); and enqueue `settlement.payout` (J7). A freelancer with no
  eligible items gets no settlement.
- **S5** — **Idempotent.** A settlement is unique per `(freelancerId, periodStart)`. It is created
  with an insert that ignores a conflict on that key (`createMany` with `skipDuplicates`, i.e.
  `ON CONFLICT DO NOTHING`) followed by a read — never Prisma's `upsert`, which is a
  find-then-insert and can raise P2002 inside the transaction. If the settlement already existed,
  the transaction **first** makes a conditional write on it requiring `status = SCHEDULED`
  (taking its row lock); if that matches nothing — the payout has already moved it on — the
  items stay unsettled for the next batch and nothing else is written. Otherwise newly eligible
  items are attached and the totals recomputed as the sums of all its items (M5), in the same
  transaction, without a second notification (the payout job is deduplicated). Items are attached
  with a conditional write on "no settlement yet", so no item is ever in two settlements.
- **S6** — One freelancer's failure rolls back only that freelancer's transaction; the batch
  carries on with the others and then fails the job, so the queue retries it (rule 11 backoff)
  and the retry skips what is already settled. A soft-deleted freelancer still gets a settlement,
  without the notification.

### Payout (`settlement.payout`, J7)
- **S7** — Runs only when the settlement's current `scheduledPayoutAt` equals the one in the job
  payload (otherwise it was rescheduled and a newer job owns it) and the settlement is
  `SCHEDULED`, or `FAILED` with `payoutAttempts < 3`. Anything else is a successful no-op.
- **S8** — No payout account, or the freelancer is soft-deleted → `ON_HOLD`, and the freelancer is
  notified (`SETTLEMENT_ON_HOLD`) unless soft-deleted. `payoutAttempts` is unchanged.
- **S9** — Otherwise, in one transaction, the settlement becomes `PROCESSING`, `payoutAttempts` +1,
  and the account is snapshotted onto it: `bankName`, `accountNumberMasked`, `accountHolder`
  (never the full number). The transition is a conditional write (`SCHEDULED | FAILED →
  PROCESSING`) that **returns the row**, and the provider is asked to transfer **the `netAmount`
  that write returned** — never a value read earlier, so items attached by a concurrent batch
  (S5) are either in the transfer or left for the next settlement. A `SCHEDULED` settlement
  therefore pays to whatever account exists at payout time.
- **S17** — The transaction that decides between S8 and S9 **starts by locking the freelancer's
  `User` row** (`SELECT id FROM "User" WHERE id = $1 FOR UPDATE`, raw SQL) and only then reads the
  payout account. Payout-account writes take the same lock first (PA7), so an account change or
  deletion and a payout decision for one freelancer never interleave: whichever locks first
  commits first, and the other reads its result. (Locking the account row alone would not cover
  an account being *created* while the payout finds none.)
- **S10** — Transfer succeeds → `PAID` with `paidAt = now` and the provider's
  `providerReference`; the freelancer is notified (`SETTLEMENT_PAID`).
- **S11** — Transfer fails → `FAILED` with `failureReason`. If `payoutAttempts < 3`,
  `scheduledPayoutAt = now + 24 h` and a new payout job is enqueued for it (no notification);
  at 3 the failure is final and the freelancer is notified (`SETTLEMENT_FAILED`). A transfer
  failure is a domain outcome — the job itself succeeds.
- **S12** — A settlement left `PROCESSING` (the runner died between the snapshot and the
  outcome) is **not** retried automatically: whether money moved is unknown, and paying twice is
  worse than waiting for an operator. While it is `PROCESSING` the payout account is locked
  (PA6).

### Objects
- **S13** — A **settlement object** is `{ id, freelancerId, periodStart, periodEnd,
  scheduledPayoutAt, status, itemCount, grossAmount, feeAmount, feeVatAmount, netAmount,
  payoutAttempts, bankName, accountNumberMasked, accountHolder, providerReference,
  failureReason, paidAt, createdAt, updatedAt }`. It never contains a full account number.

### `GET /` — FREELANCER
- **S14** — The caller's settlements, newest period first (`periodStart` desc). Query `status`
  optional (one of the five), `page` default 1, `limit` default 20 capped at 50; other values →
  **400** (CT2's rules). Response `{ settlements, meta: { total, page, limit, totalPages } }`
  with settlement objects (no items). A CLIENT → **403** `Insufficient permissions`.

### `GET /summary` — FREELANCER
- **S15** — Responds **200** with:
  - `unsettled: { count, gross, fee, vat, net }` — the caller's items not yet in a settlement;
  - `scheduled: { count, net }` — settlements awaiting payout: `SCHEDULED`, `PROCESSING`, or
    `FAILED` with attempts remaining;
  - `onHold: { count, net }` — `ON_HOLD` settlements;
  - `failed: { count, net }` — `FAILED` settlements with no attempts left;
  - `paidTotal` — sum of `netAmount` over `PAID` settlements;
  - `nextBatchAt` — the next Monday 03:00 KST strictly after now;
  - `nextPayoutAt` — the earliest `scheduledPayoutAt` among `scheduled`, or `null`;
  - `hasPayoutAccount` — boolean.

  Every settlement falls in exactly one of `scheduled`, `onHold`, `failed` or `paidTotal`. All
  zero / `null` for a freelancer with nothing yet. The path is not taken for an id.

### `GET /:id` — FREELANCER, the owner
- **S16** — Missing → **404** `Settlement not found`; another freelancer's → **403**
  `Not authorized`. Responds **200** with the settlement object plus `items`, ordered by
  `approvedAt` ascending, each `{ id, milestoneId, milestoneTitle, milestoneSequence, contractId,
  projectId, projectTitle, projectDeleted, grossAmount, feeRateBps, feeAmount, feeVatAmount,
  netAmount, approvedAt }`. A soft-deleted project changes nothing but `projectDeleted` (S2).

## Payout account — `/api/users/me/payout-account`

One account per freelancer, where settlements are paid. All three routes are expansion routes
for FREELANCER only (a CLIENT → **403** `Insufficient permissions`). The account number is stored
in plaintext and masked in every response. **[Q22]**

- **PA1** — A **payout account object** is `{ bankCode, bankName, accountNumberMasked,
  holderName, createdAt, updatedAt }` (M23 masking). The full number never appears in any
  response, log line or settlement.
- **PA2** — `GET` → **200** `{ payoutAccount }`: the caller's account object, or `null`.
- **PA3** — `PUT` creates or replaces the account. Body `{ bankCode, accountNumber, holderName }`.
  Check order and messages:
  1. validation → **400**: `bankCode` not in the list → `bankCode: Unknown bank code`;
     `accountNumber` not 10–14 digits after removing hyphens and spaces →
     `accountNumber: Account number must be 10 to 14 digits`; `holderName` empty after trimming →
     `holderName: Account holder is required` (M23)
  2. `holderName` is not the caller's name (M23) → **400** `Account holder must match your name`
  3. inside the transaction of PA4, after its user-row lock (PA7): the caller has a
     `PROCESSING` settlement → **409**
     `Payout account cannot be changed while a payout is processing`, and nothing is written
- **PA4** — On success, **in one transaction**: the account is upserted (digits only, trimmed
  holder name; a Prisma `upsert` is safe here because PA7 serializes one user's writes); every
  `ON_HOLD` settlement of the caller becomes `SCHEDULED` with `scheduledPayoutAt` = the next
  Wednesday 10:00 KST strictly after **both** now and its current `scheduledPayoutAt` (today if it
  is a Wednesday before 10:00 and the old date is earlier), `failureReason` cleared and
  `payoutAttempts` kept, and a `settlement.payout` job is enqueued for that new time. The second
  bound keeps the new job's `dedupeKey` distinct from the payout that put the settlement on hold,
  even when the runner's clock was ahead of the API's. Responds **200**
  `{ payoutAccount, rescheduledCount }`.
- **PA5** — `DELETE` → in one transaction, after the user-row lock (PA7): the caller has a
  `PROCESSING` settlement → **409** (PA3's message) and nothing is written; otherwise the account
  is removed and the response is **200** `{ payoutAccount: null }`.
  Deleting when there is no account also answers 200 (idempotent).
- **PA7** — `PUT` and `DELETE` run in a transaction whose **first statement locks the caller's
  `User` row** (`SELECT id FROM "User" WHERE id = $1 FOR UPDATE`, raw SQL), the same lock the
  payout decision takes (S17). The `PROCESSING` check of PA3/PA5 is made under that lock, so it
  cannot go stale between check and write.
- **PA6** — Only `PROCESSING` locks the account. `SCHEDULED` settlements are not affected by a
  change or deletion — they use whatever account exists when their payout runs (S9), and go
  `ON_HOLD` if there is none (S8).

## Conversations — `/api/conversations`

Every contract has exactly one conversation between its two parties. It opens when the contract is
created, carries the parties' text messages and attachments, and logs contract and milestone
events as system messages. There is no real-time channel: clients poll (MG20). All routes are
expansion routes (rule 12) open to either role; the only authorization is being a participant.

### Constants
- **MG1** — Every messaging constant, stated once:

  | Constant | Value |
  |---|---|
  | message `body` | 0–5,000 characters after trimming (JavaScript length); at least 1 when the message has no attachment |
  | attachments per message | rule 12's attachment policy: 0–5 files, 10 MB each; keys `messages/<conversationId>/<uuid>.<ext>` |
  | delete window | strictly less than 5 minutes after `createdAt` |
  | posting after completion | until `closesAt = completedAt + 30 × 24 h` (exclusive) — exact hours, not KST calendar days |
  | conversation list | `page` and `limit` exactly as CT2 (default 20, capped at 50) |
  | message page | `limit` default 30, capped at 100 (a larger value yields 100) |
  | unread digest delay | 10 minutes after the message (J8) |
  | unread digest throttle | at most one digest email per conversation and recipient per 60 minutes (J8, NC16) |
  | polling | open thread every 5 s while the page is visible; unread badge every 30 s (MG20) |

### Objects and invariants
- **MG2** — A conversation belongs to exactly one contract (`contractId` unique) and has exactly two
  participants, the contract's client and freelancer (`(conversationId, userId)` unique). Nobody
  else is ever a participant and participants never change. A message is either `TEXT` — a
  `senderId` that is one of the participants and `systemEvent: null` — or `SYSTEM` — `senderId:
  null` and a `systemEvent` from MG6.
- **MG3** — **Creation.** The accept-application transaction creates the contract's conversation,
  both participants with `lastReadAt: null`, and the `CONTRACT_CREATED` system message
  (Applications, step 7). Contracts that existed before the expansion got their conversation and
  both participants from the migration, with no messages (`lastMessageAt: null`) and `createdAt`
  equal to the contract's. **[C2]**
- **MG4** — A **message object** is `{ id, conversationId, kind, systemEvent, sender, body,
  deleted, attachments, createdAt, readByCounterpart }`:
  - `sender` is `{ id, name, profileImage }`, shown as stored even when that user is
    soft-deleted (Q11), or `null` for a system message;
  - `deleted` is `true` once the sender deleted it (MG17); a deleted message is a **tombstone**
    with `body: ''` and `attachments: []`;
  - each attachment is `{ id, url, fileName, mimeType, size, createdAt }`, `fileName` the original
    UTF-8 name (rule 12), `url` a public URL **[Q21]**;
  - `readByCounterpart` is, for a `TEXT` message sent by the caller, whether the other
    participant's `lastReadAt >= createdAt` (the messenger's read mark), and `null` for every
    other message.
- **MG5** — A **conversation object** is `{ id, contractId, myRole, contract: { id, status,
  completedAt }, project: { id, title }, counterpart: { id, name, profileImage }, lastMessageAt,
  createdAt, unreadCount, myLastReadAt, counterpartLastReadAt, canSend, closedReason, closesAt }`.
  `myRole` is `CLIENT` or `FREELANCER`, the caller's side of the contract; `counterpart` is the
  other participant, shown as stored when soft-deleted (Q11); `unreadCount` is MG8 for the caller;
  `canSend`, `closedReason` and `closesAt` are MG9's. No email address appears.

### System messages
- **MG6** — System messages are posted in the transaction of the event they record (rule 6), with a
  fixed Korean `body`. The wording is not part of this spec: tests assert `kind: SYSTEM`,
  `systemEvent` and `sender: null`.

  | `systemEvent` | Posted by |
  |---|---|
  | `CONTRACT_CREATED` | accepting an application (MG3) |
  | `MILESTONE_PLAN_UPDATED` | every plan replacement (MS8), whether or not a signature was present — unlike the notification |
  | `CONTRACT_ACTIVATED` | the signature that activates the contract (CT8) |
  | `MILESTONE_FUNDED` | funding that transitions the milestone (PY7) — not the no-op |
  | `MILESTONE_SUBMITTED` | a submission (MS13) |
  | `MILESTONE_REVISION_REQUESTED` | a rejection (MS19) |
  | `MILESTONE_APPROVED` | a manual approval (MS16) |
  | `MILESTONE_AUTO_APPROVED` | an automatic approval (MS20) |
  | `CONTRACT_COMPLETED` | contract completion (MS17), after that approval's own message |

  A step whose conditional write loses (MS4, PY7's no-op) posts nothing, so each event is logged
  exactly once. An approval of a milestone whose project is soft-deleted (MS17's deleted-project
  case) posts no system message, just as it creates no notification. A system message is posted
  whatever MG9 says — the closing rules apply to people, not to events.
- **MG7** — **Posting and ordering.** Both kinds are written by one routine that, inside the
  caller's transaction:
  1. locks the conversation row (`SELECT "lastMessageAt" FROM "Conversation" WHERE id = $1 FOR
     UPDATE`, raw SQL);
  2. sets `createdAt = max(server clock, lastMessageAt + 1 ms)`, reading the clock only after the
     lock is held;
  3. inserts the message and its attachment rows;
  4. sets the conversation's `lastMessageAt` to that `createdAt`.

  Within one conversation `createdAt` is therefore **strictly increasing in commit order**, which
  the cursors (MG14) and the read watermark (MG16) rely on: a poller never misses a message that
  commits after its cursor, and every message older than a watermark had committed when the
  watermark was taken. `createdAt` is deliberately the server clock, never a `now` handed in by the
  caller — an exception to rule 11, so that a system message written by a job run with a future
  `now` still sorts by when it was written.
  A contract **without a conversation** (impossible after MG3 — a data-repair case, or a test
  fixture made with `makeContract` alone) posts nothing: the routine logs a `warn` line and returns,
  and the event it would have recorded proceeds unchanged. It never throws for this.
  **Lock order:** `Contract` → `Milestone` → the event's other writes (`Project`, submission,
  …) → `Conversation`. Payment funding is the exception: `POST /api/payments/confirm` and
  `/dev-complete` write the `Payment` row **before** the `Milestone` (PY6, PY11), then the
  conversation. A system message is always the **last** write of its event
  transaction (`CONTRACT_COMPLETED` after `MILESTONE_APPROVED`), so the conversation lock is taken
  last; nothing that holds a conversation lock goes on to lock a contract, milestone or project.
  The participant row is only ever locked on its own (MG16, J8).

### Unread state and who may post
- **MG8** — **Unread count** of a conversation for a participant: its messages with `kind = TEXT`,
  sent by the **other** participant, not deleted, and `createdAt > ` the participant's
  `lastReadAt` (all of them while `lastReadAt` is null). System messages never count, nor do the
  caller's own messages; a message deleted after it was counted stops counting. Conversations
  under MG10 count nowhere.
- **MG9** — **Who may post**, evaluated top to bottom; the first matching row decides:

  | Condition | `canSend` | `closedReason` | `POST …/messages` |
  |---|---|---|---|
  | contract `COMPLETED` and now ≥ `closesAt` | `false` | `CONTRACT_CLOSED` | **409** `This conversation is closed` |
  | the other participant is soft-deleted | `false` | `COUNTERPART_INACTIVE` | **409** `The other participant is no longer active` |
  | otherwise — `PENDING`, `ACTIVE`, or `COMPLETED` before `closesAt` | `true` | `null` | allowed |

  `closesAt` is `completedAt + 30 × 24 h` for a `COMPLETED` contract and `null` otherwise. Reading,
  marking read and deleting one's own message within its window stay allowed in every row. A
  soft-deleted caller is 401 on every route (rule 12).
- **MG10** — **Soft delete** (rule 5): a conversation whose contract's project is soft-deleted is
  **404** `Conversation not found` on every route below, is left out of `GET /api/conversations`,
  and is excluded from every unread total (MG12, MG18, MG19). A participant's soft deletion hides
  nothing: the conversation, its messages and that participant's name stay visible to the other
  party (MG4, MG5), and only posting changes (MG9).

### `GET /api/conversations` — either role
- **MG11** — The caller's conversations, MG10 excluded, ordered by `lastMessageAt` descending with
  conversations that have no message last, then `createdAt` descending, then `id` ascending. Query
  `page`/`limit` exactly as CT2, including its 400s. Response `{ conversations, meta: { total,
  page, limit, totalPages } }`, each entry a conversation object (MG5) plus `lastMessage` — the
  newest message as a message object (MG4; a tombstone if deleted), or `null`.

### `GET /api/conversations/unread-count` — either role
- **MG12** — `{ unreadCount }`, the sum of MG8 over the caller's conversations (MG10 excluded).
  Registered before `/:id`, so the path is never read as an id.

### `GET /api/conversations/:id` — a participant
- **MG13** — Missing, or MG10 → **404** `Conversation not found`; the caller is not a participant →
  **403** `Not authorized`. Responds **200** `{ conversation }` (MG5). The same 404 / 403 pair, in
  that order, opens every `/:id` route below.

### `GET /api/conversations/:id/messages` — a participant
- **MG14** — Query: `before` or `after`, a message id (optional, at most one of them), and `limit`
  (MG1). Check order:
  1. validation → **400**: both cursors → `before: Use either before or after, not both`; a bad
     `limit` or a repeated parameter as CT2;
  2. 404 / 403 per MG13;
  3. a cursor that is not a message of this conversation → **400**
     `before: Message not found in this conversation` (or `after: …`). A deleted message is a
     valid cursor.

  | Cursor | `messages` | `hasMore` |
  |---|---|---|
  | none | the newest `limit` messages | older messages exist |
  | `before=X` | the `limit` messages immediately older than X | still older messages exist |
  | `after=X` | the `limit` messages immediately newer than X | still newer messages exist — the poller asks again at once |

  `messages` is always in ascending `(createdAt, id)` order and includes system messages and
  tombstones. Responds **200** `{ messages, hasMore }`. Reading does **not** mark anything read.

### `POST /api/conversations/:id/messages` — a participant
- **MG15** — `multipart/form-data` with a `body` field and zero or more `files` (rule 12's
  attachment policy; its 413 / 400 come before validation). A JSON body `{ body }` is accepted
  when there are no files. Check order:
  1. validation → **400**: `body` longer than 5,000 after trimming →
     `body: Message must be at most 5000 characters`; `body` empty after trimming and no files →
     `body: Message or attachment is required` (MG1);
  2. 404 / 403 per MG13;
  3. MG9: **409** `This conversation is closed`, then **409**
     `The other participant is no longer active`;
  4. the files are stored (MG1 keys); a storage failure → **502** and nothing is written;
  5. **in one transaction**: the message is posted per MG7 (`kind: TEXT`, `body` trimmed, one
     attachment row per file) and the unread digest is scheduled for the other participant under
     J8's enqueue rule (skipped while one is already pending; J8 step 2 re-checks the timing).

  Steps 2–3 are not repeated inside the transaction: a counterpart soft-deleted in between does not
  undo the send. Files stored by a request whose transaction fails stay in the bucket unreferenced.
  Responds **201** `{ message }` (MG4). Sending creates no `Notification` row (MG20) and does not
  move the sender's own `lastReadAt`.

### `POST /api/conversations/:id/read` — a participant
- **MG16** — No body. 404 / 403 per MG13, then allowed whatever MG9 says. Moves the caller's
  `lastReadAt` up to the `createdAt` of the newest message sent by the **other** participant
  (deleted ones included) — a conditional write `lastReadAt IS NULL OR lastReadAt < t`, so the
  watermark never moves back and concurrent calls are harmless. Without such a message nothing
  changes. System messages never move it: their timestamps cannot mark later text as read.
  Responds **200** `{ lastReadAt, unreadCount }` — the caller's watermark after the call and MG8
  recomputed (0 unless a message arrived meanwhile).

### `DELETE /api/conversations/:id/messages/:messageId` — the sender
- **MG17** — Check order: 404 / 403 per MG13; message missing or in another conversation → **404**
  `Message not found`; a system message or the other participant's message → **403**
  `Not authorized`; already deleted → **200** with the tombstone (idempotent); `now ≥ createdAt +
  5 min` → **409** `Messages can only be deleted within 5 minutes`. The deletion is the conditional
  write `deletedAt IS NULL AND createdAt > now − 5 min`; when it matches nothing the row is read
  again and the answer is the 200 or the 409 above. Responds **200** `{ message }`, the tombstone.
  Deletion is soft: the message and its attachment rows stay, `lastMessageAt` is unchanged, the
  stored files are **not** removed (Q21), and the message stops counting as unread (MG8). Allowed
  whatever MG9 says. Messages cannot be edited.

### `GET /api/contracts/:id/conversation` — either party
- **MG18** — An expansion route on the contracts router. Contract missing or its project
  soft-deleted → **404** `Contract not found`; not a party → **403** `Not authorized`; no
  conversation (impossible after MG3 — a data-repair case) → **404** `Conversation not found`.
  Responds **200** `{ id, unreadCount }`.
- **MG19** — Each entry of `GET /api/contracts` (CT3) also carries `unreadMessageCount`, MG8 for
  the caller (0 when the conversation is missing).

### Notifications, polling and the unread digest
- **MG20** — Messages create **no** in-app `Notification` row; the in-app notification types stay the 19
  of the Notifications table. Clients poll: an open thread calls `GET …/messages?after=<newest
  id>` every 5 s while the page is visible and `POST …/read` once new counterpart messages are on
  screen; the unread badge calls `GET /api/conversations/unread-count` every 30 s and after a
  thread is read. Every `GET` in this section is read-only (contrast rule 7), so polling never
  writes.
- **MG21** — The out-of-band signal is a digest email of unread messages (J8). MG15 schedules it;
  the handler's steps 1–2 decide whether a send is still due, and steps 3–4 (NC16) apply the
  60-minute throttle and send the email-only `MESSAGE_UNREAD_DIGEST` through `notify()`, recorded
  as an `EmailDelivery` with `contextKey = conversation:<id>`.

## Portfolio and careers — `/api/users`

Freelancers describe their work with portfolio items and career entries, shown on their public
profile. The writes are expansion routes for FREELANCER only (`authenticate → requireActiveUser
→ requireRole('FREELANCER') → [imageUpload] → validate`). The two list reads are **public** — no
token, like `GET /api/users/:id` — and are the only expansion routes outside rule 12's guard chain;
they must never read `req.user`.

### Constants and objects
- **PF1** — Every constant, stated once (lengths are JavaScript string lengths after trimming;
  an optional text field sent empty is stored as `null`):

  | Constant | Value |
  |---|---|
  | portfolio items per user | at most 20 |
  | portfolio `title` | 1–100 |
  | portfolio `description`, career `description` | 0–2,000 |
  | portfolio `url` | an absolute `http`/`https` URL of at most 2,000 |
  | portfolio `role` (the freelancer's role in the work) | 0–100 |
  | portfolio `skills` | at most 10 after normalization through `SKILL_ALIASES` and de-duplication; each 1–50 |
  | portfolio image | rule 12's image policy (field `image`, one file, 5 MB); key `portfolio/<uuid>.<ext>` |
  | career entries per user | at most 30 |
  | career `company`, `position` | 1–100 each |
  | career `employmentType` | `FULL_TIME`, `CONTRACT`, `FREELANCE` or `INTERN` |
- **PF2** — **Months.** Portfolio `startedAt`/`endedAt` and career `startDate`/`endDate` are
  calendar months written `YYYY-MM` (month `01`–`12`), stored as the first instant of that month in
  KST (`2025-03` → `2025-02-28T15:00:00.000Z`) and returned as `YYYY-MM` strings again, never as
  timestamps. The current month is the KST month containing now; a later month → 400. Where both
  ends are present the end must not be before the start (equal is allowed).
- **PF3** — A **portfolio item object** is `{ id, userId, title, description, url, imageUrl, role,
  skills, startedAt, endedAt, sortOrder, createdAt, updatedAt }`.
- **PF4** — A **career object** is `{ id, userId, company, position, employmentType, startDate,
  endDate, description, createdAt, updatedAt }`. `endDate: null` is a current position; several
  current positions may coexist.
- **PF5** — **Order.** Portfolio items: `sortOrder` ascending, then `createdAt` descending, then
  `id` ascending. Careers: `startDate` descending, then current ones first, then `endDate`
  descending, then `createdAt` descending, then `id` ascending.
- **PF6** — **`careerSummary`** is `{ totalMonths, years, months }`. Each entry covers its months
  inclusively from `startDate` through `endDate` (a current one through the current month);
  overlapping or adjacent ranges are merged and each month counted once; `years =
  floor(totalMonths / 12)`, `months = totalMonths % 12`. Example: `2020-01…2021-06` and
  `2021-03…2022-02` merge into `2020-01…2022-02`, 26 months — 2 years 2 months; `2024-05…2024-05`
  alone is 1 month; no entries → all zero. It is for display and never changes `experienceYears`.

### Writes — common rules
- **PF7** — Check order of every write: role (a CLIENT → **403** `Insufficient permissions`) →
  upload policy (portfolio only: 413 / 400) → validation (400) → existence (**404** `Portfolio item
  not found` / `Career not found`) → ownership (another user's row → **403** `Not authorized`, rule
  3) → limits (409). The messages quoted below are exact; for a wrong JSON type only the
  `<path>: ` prefix is asserted (as MS5).
- **PF8** — **Serialization.** Creating a portfolio item or career entry, and reordering the
  portfolio, run in a transaction whose **first statement locks the caller's `User` row** (`SELECT
  id FROM "User" WHERE id = $1 FOR UPDATE`, raw SQL — the lock PA7 and S17 take), and only then
  count, compute `sortOrder` and write. **Deleting a portfolio item takes the same lock first**
  (PF11). Two creates racing at 19 items end with 20 items and one 409, never 21; a reorder never
  interleaves with a create or delete, so it never writes a row deleted under it. Updates and
  career deletes take no lock: they change neither the count nor the portfolio order.

### `POST /api/users/me/portfolio` — FREELANCER
- **PF9** — `multipart/form-data` with an optional `image`, or a JSON body when there is no image.
  Fields `title` (required), `description`, `url`, `role`, `skills` (repeated fields or one
  comma-separated value; in JSON also an array of strings), `startedAt`, `endedAt`. Validation →
  **400**:
  - `title: Title is required`, `title: Title must be at most 100 characters`;
  - `description: Description must be at most 2000 characters`;
  - `url: URL must be an http or https URL` (also for one longer than 2,000);
  - `role: Role must be at most 100 characters`;
  - `skills: At most 10 skills are allowed`, `skills: Each skill must be at most 50 characters`;
    a non-string skill is a 400 too (no D16 on this route);
  - `startedAt: Month must be a YYYY-MM month`, `startedAt: Month cannot be in the future` (the
    same for `endedAt`), `endedAt: End month must not be before start month`, and an `endedAt`
    without `startedAt` → `endedAt: Start month is required with an end month`.

  Then the caller already has 20 items → **409** `Portfolio is limited to 20 items` — checked once
  before the image is stored and again under PF8's lock. The image is stored (failure → **502**,
  nothing written), then in PF8's transaction the item is created with `sortOrder` = the caller's
  highest + 1 (0 for the first item). A request that loses the race at the lock is the 409, and
  its stored image stays unreferenced. Responds **201** `{ item }`.

### `PATCH /api/users/me/portfolio/:itemId` — FREELANCER, the owner
- **PF10** — PF9's fields, all optional; only fields present change, an optional field sent empty
  is cleared to `null`, and `title` cannot be cleared. A new `image` replaces the old one;
  `removeImage` (`true`/`false`, a string in multipart) set to `true` clears `imageUrl`; both at once
  → **400** `removeImage: Cannot upload and remove an image at once`. The month order is checked on
  the stored row merged with the patch, so that check comes after existence and ownership, with
  PF9's messages. Then the new image is stored and the row updated (an item deleted in between →
  404). A replaced or removed image file is not deleted from storage. Responds **200** `{ item }`.

### `DELETE /api/users/me/portfolio/:itemId` — FREELANCER, the owner
- **PF11** — Hard delete, in a transaction whose first statement is PF8's `User`-row lock, so it
  serializes with a reorder (PF12); 404 / 403 per PF7 (an item deleted by a concurrent request
  while waiting → 404). The other items keep their `sortOrder` (gaps are fine) and the image file
  is not removed. Responds **200** `{ id, deleted: true }`.

### `PUT /api/users/me/portfolio/order` — FREELANCER
- **PF12** — Body `{ ids }`, an array of strings (otherwise **400**). Then, under PF8's lock:
  unless `ids` lists every one of the caller's items exactly once — nothing missing, duplicated,
  unknown or someone else's → **400** `ids: Must list each of your portfolio items exactly once`.
  Each item's `sortOrder` becomes its 0-based position. An empty list is valid for a caller with
  no items. Responds **200** `{ items }` in the new order.

### `POST /api/users/me/careers` — FREELANCER
- **PF13** — JSON body. `company`, `position`, `employmentType` and `startDate` are required;
  `endDate` absent, `null` or `''` means current; `description` optional. Validation → **400**:
  `company: Company is required`, `company: Company must be at most 100 characters`,
  `position: Position is required`, `position: Position must be at most 100 characters`,
  `employmentType: …` (zod's enum message, prefix asserted), PF9's month messages for `startDate`
  and `endDate` (`endDate: End month must not be before start month`), and
  `description: Description must be at most 2000 characters`. Then 30 entries already → **409**
  `Careers are limited to 30 entries`, checked under PF8's lock. Responds **201** `{ career }`.

### `PATCH /api/users/me/careers/:careerId` — FREELANCER, the owner
- **PF14** — PF13's fields, all optional, with PF10's partial-update rules; `endDate: null` or `''`
  makes the position current. The month order is checked on the merged row after existence and
  ownership. Responds **200** `{ career }`.

### `DELETE /api/users/me/careers/:careerId` — FREELANCER, the owner
- **PF15** — Hard delete; 404 / 403 per PF7. Responds **200** `{ id, deleted: true }`.

### Public reads
- **PF16** — `GET /api/users/:id/portfolio` — public. The user missing or soft-deleted → **404**
  `User not found`. Responds **200** `{ items }` in PF5 order, unpaginated — PF1 bounds it at 20. A
  CLIENT's list is `[]`.
- **PF17** — `GET /api/users/:id/careers` — public. Same 404. Responds **200** `{ careers,
  careerSummary }`, unpaginated (at most 30).
- **PF18** — `GET /api/users/:id` additionally returns `portfolioItems` (PF16's list), `careers`
  and `careerSummary` (PF17's). **[C10]**
- **PF19** — There is no `GET /api/users/me/portfolio` or `/me/careers`: those paths are PF16 and
  PF17 with the id `me`, so → 404 `User not found`. An editor reads its own rows through PF16/PF17
  with its user id.
- **PF20** — **Soft delete** (rule 5): a soft-deleted user's items and entries are kept but
  invisible — PF16–PF18 are 404 for that user and recommendations skip them (RC3) — and the user
  can no longer write (401, rule 12). Items and entries have no `deletedAt`; deleting one is
  final.

### Recommendations — common rules
- **RC1** — Both recommendation routes are **read-only** (no lifecycle sweep; contrast rule 7) and
  are computed at the request's `now`. Query `limit` only: default 10, **capped at 20** (a larger
  value yields 20); zero, negative, fractional, trailing garbage or repeated → **400**. There is no
  `page`. Each works in two stages: a database **prefilter** with a fixed `orderBy` cut to its
  first **200** rows — the order is applied before the cut, so which rows enter never varies
  between runs — then scoring in memory. A score is out of 100, rounded to two decimals
  (`Math.round(x × 100) / 100`), and results are sorted by the rounded score.
- **RC2** — **Skill matching.** Both sides' skills go through `normalizeSkill` and are compared
  exactly (case-sensitive), so `PostgreSQL` matches `SQL`; prefilters use
  `expandSkillSearchTerms` with `hasSome`, so rows stored under an alias still enter. `matched` is
  the set of the project's normalized required skills that the freelancer has, and `matchedSkills`
  lists it in the project's order. Against a project with no required skills every skill
  component is 0 and `matchedSkills` is `[]`.

### `GET /api/projects/:id/recommended-freelancers` — CLIENT, the project's owner
- **RC3** — Check order: role (**403** `Insufficient permissions`) → validation → project missing
  or soft-deleted → **404** `Project not found` → not the owner → **403** `Not authorized`. Any
  project status. Prefilter: users with role `FREELANCER`, `deletedAt` null, non-empty `skills`,
  non-null `activityCategory`, `experienceYears >= 0` and `hourlyRate > 0`; **no application to
  this project** in any status; and, when the project has required skills, `skills` overlapping
  them (RC2). Ordered by `createdAt` ascending, then `id` ascending; first 200. Candidates that
  still fail `isProfileComplete` (a blank `activityCategory`) are then dropped.
- **RC4** — Score, out of 100:

  | Component | Points |
  |---|---|
  | skills | `|matched| / |required| × 50` |
  | portfolio | `|required skills found in the skills of any of the candidate's portfolio items| / |required| × 10` |
  | category | 15 when `activityCategory` equals the project's `category` exactly (stored values, no trimming — as RC6's prefilter compares them) |
  | rating | `avgRating / 5 × 15`; 9 (= 0.6 × 15) with no reviews |
  | experience | `min(experienceYears, 10) / 10 × 10` |

  Sorted by score descending, then `reviewCount` descending, then `id` ascending. Example: required
  `[React, Node.js, SQL]`; candidate skills `[React, PostgreSQL, Java]`, portfolio skills
  `[React]`, same category, two reviews averaging 4.5, 4 years → 33.333… + 3.333… + 15 + 13.5 + 4
  = 69.1666… → **69.17**.
- **RC5** — Responds **200** `{ freelancers }`, at most `limit`, each `{ id, name, profileImage,
  activityCategory, experienceYears, hourlyRate, skills, score, matchedSkills, avgRating,
  reviewCount, portfolioPreview }`: `avgRating` is the mean of the received ratings (`null` with
  none), `portfolioPreview` the first 3 portfolio items in PF5 order as `{ id, title, imageUrl }`.
  No email address appears.

### `GET /api/users/me/recommended-projects` — FREELANCER, complete profile
- **RC6** — Check order: role (**403** `Insufficient permissions`) → complete profile (rule 4:
  **403** `프로필을 먼저 완성해주세요`) → validation. Prefilter: `status = OPEN`, `deadline >= now`,
  `deletedAt` null, **no application from the caller** in any status, and either `requiredSkills`
  overlapping the caller's skills (RC2) **or** `category` equal to the caller's

  without required skills therefore enters only through its category. `UPCOMING` projects are not
  candidates, and with no sweep an `OPEN` project past its deadline is excluded by the `deadline`
  condition, not by its status. Projects of a soft-deleted client are not excluded (Q11).
- **RC7** — Score, out of 100 (`age = now − project.createdAt`):

  | Component | Points |
  |---|---|
  | coverage | `|matched| / |project's required skills| × 50` |

- **RC8** — Responds **200** `{ projects }`, at most `limit`, each `{ id, title, category, budget,

## Notification channels — `/api/notifications/preferences`

A notification reaches its recipient over up to two channels: **in-app** (a `Notification` row,
see [Notifications](#notifications--apinotifications)) and **email** (an `EmailDelivery` row that
the `notification.email` job sends, J9). Which channels one notification uses is decided per
recipient and per type inside `notify()`, from a fixed policy and the recipient's preferences. No
external account is involved: the default mail provider writes each email to the log. Both routes
are expansion routes (rule 12) open to either role. **[C9]**

### Constants
- **NC1** — Every notification-channel constant, stated once:

  | Constant | Value |
  |---|---|
  | notification types | the 20 of NC2: the 19 in-app types of the Notifications table and the email-only `MESSAGE_UNREAD_DIGEST` |
  | `PUT` body | `preferences`: 1–20 entries |
  | mail provider | `MAIL_PROVIDER`, read at every send: unset, empty or `log` → the log provider (NC14); any other value is unsupported |
  | sender | `MAIL_FROM`, default `WorkBridge <no-reply@workbridge.local>` |
  | link base | `CLIENT_URL` without a trailing `/`, default `http://localhost:3000` |
  | send attempts | the job's default `maxAttempts` (5), retried with the queue's backoff ([Job states](#job-states)) |
  | stored `error` | at most 2,000 characters |
  | digest delay and throttle | MG1 |

### Policy and preferences
- **NC2** — **Policy.** Each type's category, recipient, and per channel its default and whether
  the recipient may change it. A channel the recipient cannot change is **locked** — mandatory
  when on.
  Trade and money notifications are locked in-app — nobody may miss an acceptance, a signature, a
  funding, a submission, a decision or a payout — and the three that announce automatic money
  movement or a payout problem (the auto-approval reminder, a held and a failed payout) are
  locked by email too.

  | `type` | Category | Recipient | In-app | Email |
  |---|---|---|---|---|
  | `APPLICATION_CREATED` | `APPLICATION` | client | on | on |
  | `APPLICATION_ACCEPTED` | `APPLICATION` | freelancer | on, **locked** | on |
  | `APPLICATION_REJECTED` | `APPLICATION` | freelancer | on | off |
  | `PROJECT_STATUS_CHANGED` | `APPLICATION` | freelancer | on | off |
  | `CONTRACT_ACTIVATED` | `CONTRACT` | both | on, **locked** | on |
  | `MILESTONE_PLAN_UPDATED` | `MILESTONE` | freelancer | on, **locked** | on |
  | `MILESTONE_FUNDED` | `MILESTONE` | freelancer | on, **locked** | on |
  | `MILESTONE_SUBMITTED` | `MILESTONE` | client | on, **locked** | on |
  | `MILESTONE_REVISION_REQUESTED` | `MILESTONE` | freelancer | on, **locked** | on |
  | `MILESTONE_APPROVED` | `MILESTONE` | freelancer | on, **locked** | on |
  | `MILESTONE_AUTO_APPROVED` | `MILESTONE` | both | on, **locked** | on |
  | `MILESTONE_AUTO_APPROVE_REMINDER` | `MILESTONE` | client | on, **locked** | on, **locked** |
  | `MILESTONE_DUE_SOON` | `MILESTONE` | freelancer | on | on |
  | `MILESTONE_OVERDUE` | `MILESTONE` | both | on | on |
  | `CONTRACT_COMPLETED` | `CONTRACT` | both | on, **locked** | on |
  | `SETTLEMENT_SCHEDULED` | `SETTLEMENT` | freelancer | on | off |
  | `SETTLEMENT_PAID` | `SETTLEMENT` | freelancer | on, **locked** | on |
  | `SETTLEMENT_ON_HOLD` | `SETTLEMENT` | freelancer | on, **locked** | on, **locked** |
  | `SETTLEMENT_FAILED` | `SETTLEMENT` | freelancer | on, **locked** | on, **locked** |
  | `MESSAGE_UNREAD_DIGEST` | `MESSAGE` | both | off, **locked** | on |

  "both" means either party of a contract, whichever the event addresses. The digest's in-app
  channel is **locked off**: messages are seen in the conversation itself (MG20), so the digest
  never creates an in-app row.
- **NC3** — **Effective channels** of one notification for its recipient: a locked channel is
  always its NC2 default — on, except the digest's in-app channel, which is always off; an
  unlocked channel is the recipient's stored choice (NC4) when there is one, else the NC2
  default. A stored value for a locked channel (reachable only by editing the database) is
  ignored. The recipient's role plays
  no part here.
- **NC4** — **Sparse storage.** A `NotificationPreference` row (`userId`, `type`, `inApp`,
  `email`; unique per `(userId, type)`) exists only while at least one of its channels departs
  from the default. Both channel columns are nullable and `null` means "follow the NC2 default",
  so a default changed later reaches everyone who never touched that channel. A write stores a
  value equal to the default, or any value for a locked channel, as `null`, and deletes a row
  whose two columns are both `null`. A user without rows gets the defaults; the migration
  backfills nothing. A row for a type the user's role does not receive may be stored and is kept,
  so a role change keeps it.

### `GET /api/notifications/preferences` — either role
- **NC5** — Responds **200** `{ preferences }`: one entry per NC2 type that the caller's role
  receives — the role of the caller's stored row, not the token's (as PF21) — in NC2 order. That
  is 8 types for a `CLIENT` and 17 for a `FREELANCER`, both counts including the five "both"
  types. Each entry is exactly `{ type, category, inApp, email, inAppLocked, emailLocked }`:

  | Field | Value |
  |---|---|
  | `type` | the NC2 type |
  | `category` | its NC2 category: `APPLICATION`, `CONTRACT`, `MILESTONE`, `SETTLEMENT` or `MESSAGE` |
  | `inApp` | the effective in-app channel (NC3), a boolean — always `false` for `MESSAGE_UNREAD_DIGEST` |
  | `email` | the effective email channel (NC3), a boolean |
  | `inAppLocked` | `true` when in-app is locked (on or off) |
  | `emailLocked` | `true` when email is locked |

  The client supplies the Korean labels. Stored rows for types the caller's role does not receive
  are not listed. The route writes nothing.

### `PUT /api/notifications/preferences` — either role
- **NC6** — Body `{ preferences: [{ type, inApp?, email? }] }`, a **partial** update: a type not
  listed, and a channel left out of an entry, keep their current setting. Check order — every
  failure is **400**, and a failing request writes nothing at all:
  1. **shape**, reported for the first failing field (rule 12), entries in array order and `type`
     → `inApp` → `email` within an entry (`<i>` is the zero-based index):
     - `preferences` missing, not an array, empty, or longer than 20 →
       `preferences: Expected 1 to 20 entries`
     - an entry that is not an object → `preferences.<i>: Expected an object`
     - `type` not one of NC2's 20 → `preferences.<i>.type: Unknown notification type`
     - `inApp` present but not a boolean (`"false"`, `0`, `null`) →
       `preferences.<i>.inApp: Expected a boolean`; `email` likewise

     Other keys are ignored.
  2. **entry rules**, once the whole shape is valid, entries in array order, the first failure
     reported:
     1. neither `inApp` nor `email` given → `preferences.<i>: Specify inApp or email`
     2. `type` repeats an earlier entry's → `preferences.<i>.type: Duplicate notification type`
     3. `inApp: true` for `MESSAGE_UNREAD_DIGEST` →
        `preferences.<i>.inApp: MESSAGE_UNREAD_DIGEST has no in-app notifications`
     4. `inApp: false` for a locked-on in-app channel →
        `preferences.<i>.inApp: <type> in-app notifications cannot be disabled`
     5. `email: false` for a locked email channel →
        `preferences.<i>.email: <type> email notifications cannot be disabled`

  A locked channel set to its own value (`true`; `inApp: false` for the digest) passes and changes
  nothing, so a client may send GET's array back unchanged. A type the caller's role does not
  receive is accepted and stored (NC4). There is no 404, 403 or 409.
- **NC7** — The write is **one transaction** whose first statement locks the caller's `User` row
  (`SELECT id FROM "User" WHERE id = $1 FOR UPDATE`, raw SQL — the lock of PA7 and PF8), and it
  takes no other lock. Every preference write goes through this lock, so two `PUT`s of one user
  serialize and no insert can collide on `(userId, type)`: no `upsert`, no P2002 inside the
  transaction. Under the lock it reads the caller's rows for the listed types, merges each entry
  into its row (a given channel replaces the stored value, an omitted one keeps it), normalizes
  per NC4, and per type deletes the row (both columns `null`), updates it, or creates it.
  `notify()` reads preferences without a lock and sees a `PUT` entirely or not at all.
- **NC8** — Responds **200** `{ preferences }`, exactly NC5's body after the write. Sending the same
  body twice leaves the same rows and returns the same response.

### Delivery through `notify()`
- **NC9** — `notify()` (one recipient) and `notifyMany()` (several, with one query per table
  rather than per recipient) are the only way notifications are created. The four
  pre-existing types go through them too — applying, accepting and rejecting an application, closing
  a project by hand — keeping their inline Korean wording, so preferences and email apply to
  every type. **[C9]** The signatures are `notify(client, input, now = new Date()):
  Promise<Notification | null>` — the in-app row, or `null` when in-app is off —
  `notifyMany(client, inputs, now = new Date()): Promise<number>` — the number of in-app rows
  written — and `notifyRecipients(client, recipients, input, now = new Date())`, where `input` is
  `{ userId, type, title, message, href?, contextKey? }` and a job passes `ctx.now`. `client` is
  the transaction of the state change; a caller that has none (the J3–J5 notices) opens one
  around its `notify` calls, so one notice's rows and jobs commit together. Inside that
  transaction:
  1. read the recipient's `email` and `deletedAt` and their preference row for the type;
  2. when in-app is on (NC3), create the `Notification` row, as before;
  3. when email is on (NC3), the recipient is **not** soft-deleted and their `email` is not empty
     after trimming, create an `EmailDelivery` (NC11) — `status: PENDING`, `createdAt = now`,
     `notificationId` = the row of step 2 or `null`, subject and body rendered per NC13, the
     given `contextKey` — and enqueue its `notification.email` job (J9).

  A rolled-back state change therefore leaves no notification, no delivery and no job: no email
  goes out for a change that did not happen. Preferences are read once, here: changing them later
  neither cancels a `PENDING` delivery nor creates a missed one.
- **NC10** — **Soft-deleted recipients.** `notify()` never creates an `EmailDelivery` for a
  soft-deleted user, and J9 skips a delivery whose recipient was soft-deleted after it was
  created. The in-app rule is unchanged: expansion callers leave soft-deleted recipients
  out (rule 5), while the four pre-existing types still create the in-app row — the pinned Q11
  behavior of applying to a project whose client is soft-deleted. Preference rows outlive a soft
  deletion and apply again after a restore.

### Email deliveries
- **NC11** — An `EmailDelivery` row is `{ id, userId, notificationId, type, toAddress, subject,
  body, contextKey, status, attempts, provider, providerMessageId, error, sentAt, createdAt,
  updatedAt }`. `toAddress` is the recipient's address when the row was created; a later change
  does not redirect it. `contextKey` is `null` except for the digest (NC16). `attempts` is
  incremented just before every provider call. `provider` is the `MAIL_PROVIDER` value of the
  last send (`log` by default), including an unsupported one (NC14). No route reads or lists deliveries: they are the audit trail of
  what was sent, and nothing deletes them (Q24).
- **NC12** — **States.** Every transition is a write conditional on `status = 'PENDING'`, so a
  delivery leaves `PENDING` exactly once:

  | From | To | When |
  |---|---|---|
  | — | `PENDING` | `notify()` (NC9); `attempts` 0 |
  | `PENDING` | `SENT` | the provider accepted the email: `sentAt` = the job's `now`; `provider` and `providerMessageId` set; `error` cleared |
  | `PENDING` | `PENDING` | the provider threw and the job has attempts left: `error` recorded; the job retries with backoff |
  | `PENDING` | `FAILED` | the provider threw on the job's last attempt: `error` recorded; or `MAIL_PROVIDER` is unsupported: no provider call, `attempts` stays as it was, `provider` = the configured value as given, `error` per NC14 |
  | `PENDING` | `SKIPPED` | the recipient was soft-deleted before the send: `error` = `Recipient is no longer active`; no provider call |

  `SENT`, `FAILED` and `SKIPPED` are final. Delivery is **at least once**: if the provider accepts
  an email but the `SENT` write fails, the retry sends it again. The provider receives the
  delivery `id` as an idempotency key, so that a real provider can drop such a duplicate. A
  delivery can also **stay `PENDING` for good** when its job ends `FAILED` before the handler
  writes a final state — stale-lock recovery after the last attempt, or a database error on the
  last attempt's `attempts` or `SENT` write. The job's `FAILED` row (`lastError`) is then the
  record; nothing sends that delivery again (Q24).
- **NC13** — **Rendering**, done once by `notify()` and stored on the row. Plain text, Korean:
  subject `[WorkBridge] <title>`; body `<message>`, a blank line, `바로가기: <base><href>` (left
  out when `href` is `null`), a blank line, `알림 설정: <base>/my/notifications/settings`, where
  `<base>` is NC1's link base and `title`, `message`, `href` are the values `notify()` received.
  Tests assert `type`, `userId`, `toAddress`, `contextKey`, `status` and `notificationId`, never
  the wording.
- **NC14** — **Mail provider.** A provider takes `{ deliveryId, from, to, subject, text }` and
  returns a `providerMessageId`, or throws. `MAIL_PROVIDER` is read at each send. At process
  start (the server, `jobs:run`, `jobs:worker`) a set but unsupported value is reported once as a
  `warn` line `unsupported MAIL_PROVIDER`, without throwing — a bad value fails the sends that
  need it, not the process (the lazy-env principle of `src/env.ts`):
  - unset, empty or `log` → the **log provider**: one `info` line `mail.sent` with `deliveryId`,
    `from`, `to`, `subject`, `text` and the returned id `log-<uuid>`. It needs no account and no
    network, and never fails;
  - any other value → the delivery becomes `FAILED` with `error`
    `Unsupported MAIL_PROVIDER "<value>"`, and the job `FAILED` without retry.

  No real provider is connected. **[Q24]**
- **NC15** — **No unsubscribe link.** Every email is transactional — caused by an event on the
  recipient's own account — so there is no unsubscribe link, token or `List-Unsubscribe` header.
  The body's last line points to the preferences page, which requires signing in; optional types
  are turned off there (NC6), and locked ones cannot be turned off short of deleting the account.
  **[Q25]**

### Unread-message digest (J8 steps 3–4)
- **NC16** — J8 continues after its step 2, in the same transaction and under the same
  participant lock:
  3. **throttle** — take the newest `EmailDelivery` with this `userId`,
     `type = 'MESSAGE_UNREAD_DIGEST'` and `contextKey = 'conversation:<conversationId>'`, in any
     status. When its `createdAt` is later than `ctx.now` minus MG1's throttle, nothing is sent:
     unless another `PENDING` `message.unreadDigest` job exists for the pair (the running job is
     `RUNNING` and does not count), one is enqueued at that `createdAt` plus the throttle, and the
     job ends `SUCCEEDED`. Exactly one throttle period after the last digest, it sends.
  4. **send** — `notify()` with `userId` = the recipient, `type: 'MESSAGE_UNREAD_DIGEST'`,
     `contextKey: 'conversation:<conversationId>'`, `href: '/messages/<conversationId>'`, a
     message naming the project and MG8's unread count from step 2, and `ctx.now`. The delivery's
     `createdAt` is therefore `ctx.now`, which the next step 3 reads, so the throttle is exact
     under `runDueJobs({ now })`.

  The digest is email-only (NC2). When the recipient has turned it off, step 4 creates nothing,
  step 3 never finds a delivery, and each later message schedules its own job as usual. The email
  itself is sent by the delivery's `notification.email` job, which a **later** runner pass claims
  (`runDueJobs` claims once, at its start). Example with no reads: message A at t0 → digest
  delivery at t0 + 10 min; message B at t0 + 20 min schedules a job for t0 + 30 min, which finds
  the delivery 20 minutes old and re-enqueues for t0 + 70 min; at t0 + 70 min the delivery is
  exactly 60 minutes old, so one digest covering both messages is created.

## Background jobs

Postgres-backed queue (`Job` table) used by the scheduled sweeps, milestone auto-approval and
due-date notices, the weekly settlement batch and payouts, the unread-message digest (J8), and
email delivery (J9).

### Job states

| From | To | When |
|---|---|---|
| — | `PENDING` | enqueued; `runAt` defaults to now, `maxAttempts` to 5 |
| `PENDING` | `RUNNING` | claimed by a runner once `runAt <= now`; `attempts` +1, `lockedAt`, `lockedBy` set. Claims are ordered by `runAt`, then `createdAt`, and use `FOR UPDATE SKIP LOCKED`, so concurrent runners never claim the same job |
| `RUNNING` | `SUCCEEDED` | the handler returned; `completedAt` set |
| `RUNNING` | `PENDING` | the handler threw and `attempts < maxAttempts`: `runAt = now + min(30 s × 2^(attempts − 1), 1 h)`, `lastError` recorded |
| `RUNNING` | `FAILED` | the handler threw a `PermanentJobError`, the type has no handler, or `attempts` reached `maxAttempts`; `lastError` recorded and an error-level log line written |
| `RUNNING` | `PENDING` | stale-lock recovery: `lockedAt` older than 10 minutes (the runner died) and `attempts < maxAttempts`. `attempts` is not refunded |
| `RUNNING` | `FAILED` | stale-lock recovery when `attempts >= maxAttempts`: `lastError` = `stale lock, attempts exhausted` and an error-level log line, so a job that kills its runner every time does not return forever |
| `PENDING` | `CANCELLED` | by domain code that makes a job moot (none yet — the milestone and settlement handlers re-check state and end as no-ops instead, J1) |

### Recurring jobs
- Each recurring type defines its next slot after a given time and a `dedupeKey` per slot.
- `ensureRecurringJobs(now)` enqueues the next slot of every recurring type. Thanks to the
  `dedupeKey` it is safe to call any number of times.
- When a recurring job is **claimed**, the runner enqueues its next slot (the first slot after the
  claim time). The chain therefore survives a run that retries and finally fails, and a runner
  that was down for a while resumes with one catch-up run instead of a backlog.

### Runners
`runDueJobs({ now, limit = 50, types? })` claims up to `limit` due jobs, runs them one after
another, and returns `{ claimed, succeeded, retried, failed, skipped }`. Before running each job
it re-asserts its lock; a job whose lock another runner has taken over in the meantime (a batch
that outlived the 10-minute stale window) is **skipped**, never run twice. A failed bookkeeping
write is logged and leaves that one job to stale-lock recovery; the rest of the batch still runs.
It does **not** call `ensureRecurringJobs`; every production-style entry point does so first:

| Runner | Where it runs | Order |
|---|---|---|

Payloads: `milestone.autoApprove` and `milestone.autoApproveReminder` carry
`{ milestoneId, round }`; `milestone.dueSoon` and `milestone.overdue` carry `{ milestoneId }`;
`settlement.payout` carries `{ settlementId, scheduledPayoutAt }` (ISO-8601 string);
`message.unreadDigest` carries `{ conversationId, recipientId }` and has no `dedupeKey` (J8);
`notification.email` carries `{ deliveryId }` (J9); the recurring
types carry `{}`. All use the default `maxAttempts` of 5. Because the payout key contains
`scheduledPayoutAt`, a rescheduled payout (PA4, S11) is a new job and never collides with the one
it replaces.

### Milestone and settlement handler rules
- **J1** — Handlers re-read everything they act on. A job whose state no longer calls for it —
  the milestone moved on, the round is not the latest, the settlement was rescheduled or paid —
  ends **`SUCCEEDED` as a no-op**. A payload naming a milestone or settlement that does not exist
  throws `PermanentJobError` (→ `FAILED`, kept for inspection). Notifications to a soft-deleted
  user are skipped (rule 5).
- **J2** — `milestone.autoApprove` approves (MS20) if the milestone is `SUBMITTED`, its latest
  submission's `round` equals the payload's, and `autoApproveAt <= now` — **whether or not the
  contract's project is soft-deleted**. With a deleted project it completes the approval and,
  where due, the contract, but never writes the project row and creates no notification for that
  approval (MS17) — captured money is not frozen by a deletion.
- **J3** — `milestone.autoApproveReminder` notifies the client if the project is not soft-deleted,
  the milestone is `SUBMITTED`, the round matches and `autoApproveAt` is still in the future.
- **J4** — `milestone.dueSoon` notifies the freelancer if the project is not soft-deleted and the
  milestone is `FUNDED` or `REVISION_REQUESTED`.
- **J5** — `milestone.overdue` notifies both parties under J4's conditions.
- **J6** — `settlement.weeklyBatch` runs S4–S6 for the period whose `periodStart` is parsed from
  its `dedupeKey` — never from its current `runAt`, which a retry changes. A missing or
  unparseable key throws `PermanentJobError`. It does not look at project deletion; a soft-deleted freelancer's settlement is created
  without notification.
- **J7** — `settlement.payout` runs S7–S11. A soft-deleted freelancer's settlement goes `ON_HOLD`
  without notification, even if a payout account exists.

### Messaging handler rule
- **J8** — `message.unreadDigest`, payload `{ conversationId, recipientId }`, no `dedupeKey`, the
  default `maxAttempts`. **Enqueued** by MG15's transaction for the other participant, with
  `runAt` = the message's `createdAt` + 10 minutes, unless a `PENDING` job of this type with the
  same `conversationId` and `recipientId` already exists (matched on the payload). Sends to one
  conversation serialize on MG7's lock, so that check cannot race another send. There is no
  clock-bucket key: an hour-bucket `dedupeKey` would drop or double emails at the bucket edge. The
  handler uses `ctx.now` and runs **in one transaction**:
  1. lock the recipient's participant row (`SELECT … FROM "ConversationParticipant" WHERE
     "conversationId" = $1 AND "userId" = $2 FOR UPDATE`, raw SQL); no such row →
     `PermanentJobError`. `POST …/read` (MG16) writes the same row, so a read and a digest
     serialize;
  2. no-op (`SUCCEEDED`) when the conversation's project is soft-deleted, the recipient is
     soft-deleted, or MG8's unread count for the recipient is 0. Otherwise, when the **oldest**
     unread message (MG8) has `createdAt > ctx.now − 10 min` — the messages this job was enqueued
     for were read and newer ones arrived while it was pending, so the enqueue rule skipped them —
     enqueue a new job at that message's `createdAt + 10 min` (unless a `PENDING` one exists for
     the pair; the running job is `RUNNING` and does not count) and end `SUCCEEDED` without
     sending;
  3. the throttle, and 4. the email — both specified once, in NC16.

  Outcome: a message read within 10 minutes never causes an email; a conversation sends a
  recipient at most one digest per 60 minutes; unread messages that pile up in between go out
  together 60 minutes after the last digest. A duplicate `PENDING` job (a send racing step 3's
  re-enqueue) is harmless — step 3 throttles it. Example of step 2's re-check: message A at t0
  enqueues a job for t0 + 10 min; the recipient reads at t0 + 2; message B at t0 + 9 enqueues
  nothing (A's job is pending); at t0 + 10 the job finds B unread but only 1 minute old, so it
  re-enqueues for t0 + 19 and sends nothing. Tests drive it with `runDueJobs({ now })` alone.

### Email handler rule
- **J9** — `notification.email`, payload `{ deliveryId }`, `dedupeKey`
  `notification.email:<deliveryId>`, the default `maxAttempts`, enqueued by `notify()` (NC9). The
  provider call cannot be rolled back, so the handler does **not** run in one transaction; each
  write is one statement conditional on `status = 'PENDING'` (NC12):
  1. read the delivery; none → `PermanentJobError`. Not `PENDING` → no-op, `SUCCEEDED`;
     email switched off (J10) → `SKIPPED` with `error` =
     `Email sending is disabled (JOB_EMAIL_ENABLED)`, `SUCCEEDED`, no provider call;
  2. the recipient is soft-deleted → `SKIPPED`, `SUCCEEDED`;
  3. `MAIL_PROVIDER` unsupported (NC14) → `FAILED` with its `error`, then `PermanentJobError`;
  4. `attempts` + 1 — when this write matches nothing (the delivery left `PENDING` meanwhile) the
     job ends `SUCCEEDED` without sending;
  5. call the provider with `from` = `MAIL_FROM`, `to` = `toAddress` and the stored subject and
     body. On success → `SENT`. On a throw → record `error` and `provider`, and on the job's last
     attempt (its `attempts` has reached `maxAttempts`) also `FAILED`; then rethrow, so the queue
     retries with backoff or marks the job `FAILED` with its error-level line (rule 9).

  The project's soft deletion plays no part: a delivery created by an event that rule 5 allowed
  is still sent.

### Gated job types
- **J10** — Two types are switched off by environment flag until production can run them for
  real; each runs only when its flag is exactly `true`, read at every runner pass. Off by default.
  - `settlement.payout` (`JOB_PAYOUT_ENABLED`) is **held**: no runner claims it while the flag is
    off, so it stays `PENDING` with its `runAt`, and `runDueJobs` does not count it. Turning the
    flag on runs every held payout; J1 still makes a rescheduled one a no-op. A payout is money
    owed, so it is kept, not dropped. (Today's only payout provider, `LogPayoutProvider`, reports
    every transfer as successful without moving money.)
  - `notification.email` (`JOB_EMAIL_ENABLED`) is **skipped**: the job runs and J9 step 1 marks
    its delivery `SKIPPED`. Email is only useful when timely, so holding it would send a backlog
    of stale notifications and digests in one burst once the flag is turned on. This covers the
    unread-message digest (J8), whose email is a `notification.email` job; the digest job itself
    still runs and keeps its throttle.

## Internal endpoints — `/api/internal`

### `POST /jobs/run` — internal token
- Not a user route: no JWT, and any `Authorization` header is ignored.
- If `INTERNAL_JOB_TOKEN` is unset or empty, the endpoint does not exist: **404**, answered exactly
  as an unmatched path is (see Q10), so its existence is not revealed.
- `X-Internal-Token` missing or different from `INTERNAL_JOB_TOKEN` → **403**
  `Invalid internal token`. The comparison is constant-time over SHA-256 digests, so a token of
  any length is a 403, never a 500.
- Body `{ limit? }` — an integer from 1 to 500, default 50 → else **400** (rule 12 format). Checked
  after the token.
- Runs `ensureRecurringJobs(now)` → `recoverStaleJobs(now)` → `runDueJobs({ now, limit })` and
  responds **200** with `{ claimed, succeeded, retried, failed, skipped }`.

## Known divergences

Current behavior differs from the intent above. Each should get a test that **fails today**,
pinned with `it.fails`. The exception is **D20**, pinned with `it.todo`: its deadlock reproduces
only with a warm connection pool (2 of 16 full-suite runs), so an `it.fails` would pass or fail
by chance.

### Resolved

| ID | Was | Fix | Verified by |
|---|---|---|---|
| **D1** | `login`, `refresh`, `getMe`, `getUserById` and `googleCallback` omitted `deletedAt: null`, so a soft-deleted user could authenticate indefinitely and stayed publicly visible | Switched those reads to `findFirst` with `deletedAt: null`. `signup`'s duplicate-email check deliberately still ignores `deletedAt`, because `email` is unique at the database level — filtering there would report a taken address as free and then fail with P2002 | Soft-deleting a user then asserting login → 401, `GET /me` with a pre-deletion token → 404, public profile → 404, and restoring → 200 |
| **D2** | A `COMPLETED` contract could be signed again, flipping it back to `ACTIVE` | Reject signing a contract that is already `COMPLETED` (400), and wrap the signature write and the activation in one transaction with activation guarded on `status === 'PENDING'` | Re-signing a `COMPLETED` contract now returns 400 with the status preserved; 15 concurrent sign pairs still all reach `ACTIVE` |
| **D4** | P2002 on the unique `Contract.projectId` was uncaught in `updateApplication`, so a duplicate contract surfaced as a 500 | Catch P2002 around the accept transaction → **409**. Kept as a backstop even with D7 fixed, because two concurrent accepts of *different* pending applications can both pass the pre-check | Accepting a bulk-rejected sibling application returns 409 rather than 500 |
| **D7** | No check that the application was still `PENDING`, so an already-decided application could be re-decided | Reject non-`PENDING` applications with **409** before doing any work | Second accept → 409; rejecting an already-accepted application → 409 |

**Correction on D2:** this document previously claimed concurrent signing could leave a contract
with both flags set and status `PENDING`. That was wrong. `prisma.contract.update` compiles to a
single `UPDATE … RETURNING`, which takes a Postgres row lock, so the two parties serialize on it
and the second signer reads the first's committed value and activates. A probe of 15 concurrent
sign pairs produced zero stuck contracts *before* the fix. The transaction was still added — it
closes the window where a failure between the two statements leaves a contract signed-but-inactive,
and it makes the invariant local rather than dependent on an unstated locking argument — but it was
not repairing a live race. The genuine defect was the missing status guard.

## Open questions

These need a decision before they can be tested. Each is a defensible design choice, not
obviously a bug.

### Decided

- **Q1 — token invalidation: keep as is.** Tokens stay stateless. Logout clears the cookie only;
  refresh does not rotate. An access token remains valid for up to 15 minutes after logout and a
  refresh token up to 7 days. Accepted deliberately — no token store or denylist.
  - For the record, since it is easy to misread: the **access token is stored in `localStorage`**
    by the client (`authStore.js`), not in a cookie, because it must be readable to populate the
    `Authorization` header. Only the **refresh token** is a cookie, and it is `httpOnly` so
    JavaScript cannot read it. `middleware.js` route gating depends on it being a cookie, since
    Next.js middleware runs server-side and cannot see `localStorage`.
- **Q2 — `PATCH /me`: keep as is.** Fields belonging to the other role are silently ignored, not
  rejected.
- **Q3 — project editing: keep as is.** `title`/`description`/`category`/`requiredSkills` remain
  editable in any status, including `COMPLETED` and `CANCELLED`.
- **Q4 — deleting a project with a live contract: block it.** `DELETE /api/projects/:id` must
  refuse with **409** when the project has a contract that is not `COMPLETED` (i.e. `PENDING` or
  `ACTIVE`). A project whose contract has been completed may still be soft-deleted. Not
  implemented yet. **[D11]**

| ID | Question |

| **Q5** | What is `IN_PROGRESS` for? It exists in the enum and in `validTransitions`, but nothing ever assigns it — `CLOSED` currently means both "recruitment ended" and "work underway". Proposal: when `signContract` activates a contract, set the project to `IN_PROGRESS` in the same transaction; approving the last milestone (MS17) then transitions `IN_PROGRESS → COMPLETED`, which is already an allowed transition, removing today's direct `CLOSED → COMPLETED` bypass. | **Q6** | Should `GET`/`DELETE` bookmark 404 for a project id that **never existed**, as `POST` does? *(deferred.* The *soft-deleted* case is not deferred — rule 5 decides it, and the gap is tracked as **D19**.*)* |
| **Q7** | Should the unpaginated list endpoints (`GET /:id/applications`, `/me/applications`, `/api/payments`, review lists) be paginated before they grow? *(deferred)* |

Consistent with the stateless-token decision in Q1, but it is privilege-retention-after-demotion and deserves an explicit yes. Partial mitigation already in place: `POST /refresh` mints the new access token from the **freshly-read user row**, not from the refresh token's claims, so a role change does propagate on the next refresh. |

Reading `''` as "absent → default" is at least as defensible as "non-integer → 400". Both behaviors are currently pinned by tests; the spec should pick one. |

Should the pre-existing endpoints follow rule 12, or should validation come after existence everywhere? |
| **Q16** | **Email is never normalized.** `signup` stores the address verbatim, and both the duplicate check and `login` are case- and whitespace-sensitive — so `Victim@x.com` and `victim@x.com` are two separate accounts, and a user who signs up with a capitalized address cannot log in with the lowercase form. | **Q17** | A Google login whose email belongs to a **soft-deleted** account degrades to the generic `error=oauth_failed` redirect — the lookup filters `deletedAt: null` so the row is invisible, but `email` is still unique, so the create collides with P2002 and lands in the catch-all. | **Q18** | `POST /logout` sits behind `authenticate`, so a client whose 15-minute access token has already expired **cannot clear its own 7-day `httpOnly` refresh cookie** — logout only works while you still hold a live access token. Given the endpoint's purpose is to drop the long-lived credential, should it be public (or tolerate an expired token)? |
| **Q19** | Google identity matching by `googleId` never refreshes `email` or `name` from the profile, so a Google-side email change leaves WorkBridge permanently stale. Should the profile be re-synced on each login? |
| **Q20** | `CLIENT_URL` is an optional passthrough in `src/env.ts`, so if it is **unset** every OAuth redirect becomes the literal string `undefined/login?error=oauth_failed` or `undefined/auth/callback?…` rather than failing. The spec documents these targets as `${CLIENT_URL}/…` but never says what an absent value should do. Should `CLIENT_URL` be promoted to a required var — noting that would make it a boot-time failure, which is the tradeoff `src/env.ts`'s lazy getters were designed to avoid? |
| **Q21** | Message attachments (MG4, MG15) and milestone deliverables (MS2, MS13) live in the existing **public** Supabase bucket under unguessable `<folder>/<uuid>.<ext>` keys and are returned as plain public URLs. Anyone who obtains a URL — a forwarded link, a log line, a former participant — can download the file without authenticating, and nothing revokes it: deleting the message (MG17) or the user removes neither the object nor its reachability. This is the current, deliberate intent (signed URLs need a private bucket and a download endpoint), so it is not a divergence. Should attachments move to a private bucket served through short-lived signed URLs, and should deleting a message delete its files? |
| **Q22** | Payout account numbers are **stored in plaintext** (`PayoutAccount.accountNumber`) and only masked in responses (M23, PA1). There is no encryption at rest and no bank-side verification that the account belongs to the member — the holder-name rule compares against the profile name only. This is the current, deliberate intent (encryption and real-name verification carry cost and regulatory work), so it is not a divergence. Should account numbers be encrypted at rest, and under what key management? Should holder verification go through a bank API before the first payout? |
| **Q23** | The rate-limit client IP comes from `X-Forwarded-For` when `TRUST_PROXY` is set, and the Next.js proxies forward that header as received (rule 10). Behind Vercel's edge the header is rewritten, but a self-hosted Next reachable by untrusted clients lets them pick their own IP: rotating it bypasses the per-IP login limit, makes the email + IP failure limit effectively unlimited per account, and lets anyone exhaust a chosen IP's quota. Should the deployment put a header-rewriting proxy in front of Next, should self-hosted setups leave `TRUST_PROXY` unset, or should the failure limit also key on email alone? |
| **Q24** | **No real mail provider is connected** (NC14). The default `log` provider writes each email's recipient address and full text to the application log at `info`, and `EmailDelivery` rows keep the address, subject and body indefinitely — `maintenance.cleanup` does not touch them. Production has no resident job runner either (Background jobs), so today no email leaves the system anywhere. Connecting a real mail service is deliberately out of scope for now, so it is not a divergence. Which provider, with what sender-domain authentication (SPF, DKIM)? How should bounces and complaints be handled — there is no suppression list, so an address that bounces is tried again for every new delivery? How long should deliveries, which are personal data, be kept, and should a delivery stranded in `PENDING` by a failed job (NC12) be swept or re-sent? |
| **Q25** | **Optional emails have no one-click opt-out** (NC15). Turning off the unread digest or the `APPLICATION_CREATED` email requires signing in to the preferences page; nothing in the email itself stops it. All mail is transactional today, so rules aimed at advertising mail and mailbox providers' one-click requirement for bulk marketing mail do not clearly apply — but a recipient who no longer wants the digest has no low-effort way out. Should optional types carry a signed one-click link (and `List-Unsubscribe`) that turns that one type's email off without signing in? |
| **Q26** | `CLIENT_URL` is read two ways. CORS (`index.ts`) and email links (NC1, NC13) split it on commas and use the first entry, but the OAuth redirects (`GET /api/auth/google/callback`, and the failure redirect) interpolate the **raw** string, so a comma list produces `http://a.test, http://b.test/auth/callback?…`. Related to Q20 (unset value). Should OAuth also use the first entry (one shared `clientBaseUrl()`), or should `CLIENT_URL` be a single origin with extra CORS origins only in `CORS_ORIGINS`? Until decided, ENV.md says to keep it a single origin. |

### Note on `validTransitions`

The transition table governs **only manual, client-initiated changes** via
`PATCH /api/projects/:id/status`. System-initiated transitions — the lifecycle sweep, accepting an
application, signing a contract, approving the last milestone — do not consult it and are
specified in their own sections. Reading the table as a total state machine is what makes the
last approval's `CLOSED → COMPLETED` (MS17) look like a violation.

## Suggested test priority

Ordered by risk, not by convenience:

1. **Milestone approval races and settlement arithmetic** — MS21's "exactly one winner, one
   settlement item", MS22's concurrent approval of the last two milestones completing the
   contract, the fee/VAT/net table and M5's item sums, and the batch's idempotence (S5). Money moves automatically here, so a bug pays the wrong amount or pays twice.
2. **The accept-application transaction** — seven coupled writes, the most complex state change in
   the system. Assert every effect, then assert a forced failure rolls all of it back.
3. **The auth matrix** — every protected route 401s without a token, and 403s for the wrong role.
   This is the compensating control for `Express.Request.user` being typed non-optional: the
   compiler deliberately will not warn if a public handler reads `req.user`.
4. **The payment state machine, per milestone** — PY1's check order including sequential funding
   and `Milestone is already funded`, the resume/retry/replay table, the amount-mismatch
   rejection, and funding on confirm (PY7, PY9). Money paths deserve the most tests.
5. **D2 (`signContract`)** — including a genuinely concurrent two-party sign, and a plan
   replacement racing a signature (MS9).
6. **D1 (soft-delete auth bypass)** and **D7/D4 (double accept)** — small tests, real consequences.
7. **`GET /api/projects` filtering and pagination** — the widest branch surface in the codebase.
8. **The pure functions** — `normalizeSkill`, `normalizeSkillList`, `expandSkillSearchTerms`,
   `isProfileComplete`, `getProjectStatusForRecruitmentStart`, and the money and KST helpers
   (M3, M12, M19). Cheap and fast; do them last
   because they carry the least risk.

**Concurrency coverage today.** These races have deterministic tests that fail if the lock or the
conditional write is removed: S17 (the payout's user-row lock — an account created mid-decision is
never left behind `ON_HOLD`), MS9 (the plan replacement decides from the locked pre-image), PY8 (the
`FAILED` write is conditional on `PENDING`), and the D13 create collision. Known gaps, where the
existing tests pass even without the protection: **S5** — two weekly batches are never run
concurrently, so the conflict-ignoring insert and the conditional attach are exercised only
sequentially; **S9** — the conditional `SCHEDULED | FAILED → PROCESSING` write and "transfer the
returned `netAmount`" are tested only sequentially, never against a concurrent batch attaching an
item; **PA7** — removing the account write's own user-row lock is not detected by the S17 test,
because inserting the account already waits on the user row through its foreign-key check
(`FOR KEY SHARE`); the `PROCESSING` check under the lock (PA3/PA5) has no race test.
