# WorkBridge 확장 브리프

이 문서는 확장 작업 전체의 기준이다. 계획, 구현, 검증을 맡는 모든 워커가 먼저 읽는다.

## 목적

WorkBridge를 "현업 코드베이스에 가까운 규모"로 키운다. 지금 제품 코드는 약 7.5천 줄(서버 `src/` 2.7천, 클라이언트 `src/` 4.7천)이라 에이전트가 한 번에 다 읽을 수 있다. 목표는 제품 코드 약 2만 줄 이상이며, 줄 수 자체보다 **도메인 간 얽힘과 코드만 봐서는 알 수 없는 운영 규칙**을 늘리는 것이 핵심이다.

이 코드베이스는 강의 시연용이다. 수강생이 코드를 자세히 읽지는 않지만, 에이전트가 그 위에서 버그를 고치고 기능을 더하는 장면을 녹화한다. 따라서 **실제 프리랜서 플랫폼에 있을 법한 보편적이고 그럴듯한 동작**을 골라야 한다. 가장 단순한 선택지보다 현실적인 선택지를 우선한다.

## 추가할 도메인

### 1. 마일스톤과 정산

- 계약을 마일스톤 여러 개로 나눈다. 마일스톤마다 금액, 기한, 산출물 제출, 승인/반려가 있다.
- 결제는 마일스톤 단위다. 기존 `Contract`↔`Payment` 1:1이 1:N으로 바뀐다. 기존 BEHAVIOR.md와 테스트도 그에 맞게 고친다.
- 반려와 재제출: 클라이언트가 사유를 적어 반려하면 프리랜서가 다시 제출한다.
- 자동 승인: 제출 후 클라이언트가 N일(기본 7일) 안에 승인도 반려도 하지 않으면 자동 승인된다.
- 정산: 승인된 마일스톤 금액에서 플랫폼 수수료를 떼고 프리랜서 정산 내역을 만든다. 정산은 배치로 돈다(정산 주기, 상태 전이, 내역 조회).
- 수수료율과 금액 계산 규칙은 명세에 적는다. 금액 필드가 `Float`인 기존 부채는 그대로 두되, 반올림 규칙은 정한다.

### 2. 메시지

- 계약별 대화방. 계약 당사자(클라이언트, 프리랜서)만 참여한다.
- 텍스트 메시지, 파일 첨부(기존 Supabase Storage 업로드 경로 재사용), 읽음 처리, 안 읽은 메시지 수.
- 실시간은 폴링으로 충분하다. WebSocket은 넣지 않는다.

### 3. 프로필 확장

- 프리랜서 포트폴리오 항목(제목, 설명, 링크, 이미지), 경력(회사, 기간, 역할).
- 스킬 기반 프리랜서 추천: 프로젝트에 맞는 프리랜서 추천과 프리랜서에게 맞는 프로젝트 추천. 기존 `lib/skills.ts`의 정규화와 매칭을 재사용한다.
- 프로필 완성도(`lib/profileCompletion.ts`)에 새 항목을 반영한다.

### 4. 알림 채널

- 이메일 발송: 발송 인터페이스를 두고, 기본 구현은 로그 출력이다. 실제 메일 서비스 연동은 나중에 한다. 외부 계정 없이 로컬에서 동작해야 한다.
- 사용자별 알림 설정: 알림 종류별로 인앱/이메일 수신 여부.
- 기존 `Notification` 생성 지점과 연결한다.

## 인프라

기능에 필요하면 추가한다. 단, **새 외부 계정이나 배포 없이 로컬에서 돌아가야 한다.**

- 작업 큐와 스케줄러: Postgres 기반으로 만든다. 정산 배치, 자동 승인, 이메일 발송이 쓴다. 지금 `GET /api/projects`가 하는 지연 상태 갱신(`closeExpiredOpenProjects`)도 여기로 옮길지는 계획에서 정하되, 옮긴다면 기존 동작을 깨지 않아야 한다.
- 구조화 로깅, 요청 ID.
- 입력 검증(zod): **신규 도메인에만** 적용한다. 기존 컨트롤러는 그대로 둔다. 두 방식이 섞인 상태가 의도된 결과다.
- 요청 제한(rate limit): 로그인, AI 단가 분석.

넣지 않는 것: CI/CD 변경(리뷰 Action, PR/이슈 템플릿, CODEOWNERS, 브랜치 보호), Sentry, Vercel Cron, 모노레포 전환, WebSocket, 실제 이메일 서비스 연동.

## 기술 부채

버그를 일부러 심지 않는다. 이미 있는 부채(금액 `Float`, 스킬 `String[]`, GET이 DB에 쓰는 것, BEHAVIOR.md의 남은 불일치)는 고치지 않는다. 확장하면서 자연스럽게 생기는 다음 부채는 정리하지 않고 남긴다.

- 서비스 레이어는 신규 도메인에만 있고 기존 컨트롤러에는 로직이 그대로 남는다.
- 알림 생성 코드가 도메인마다 흩어져 있고 새 헬퍼로는 일부만 옮겨진다.
- 입력 검증이 zod와 수동 검사로 섞인다.

## 코드 규칙

- `CLAUDE.md`를 따른다. 특히: routes → controllers → lib 흐름, `AppError`, `prisma.$transaction`, `deletedAt: null` 필터, Prisma 생성 타입 재사용, `import 'dotenv/config'` 첫 줄 유지, `req.user`는 `authenticate` 뒤에서만.
- `docs/BEHAVIOR.md`가 명세다. 도메인마다 **명세를 먼저 쓰고** 그 명세를 기준으로 구현하고 테스트를 쓴다. 명세와 구현이 다르면 명세의 알려진 불일치 목록에 적는다.
- 테스트는 `test/`의 기존 방식(vitest + supertest, 실제 Postgres)을 따른다. 401/403/소유권 매트릭스는 `test/authorization.test.ts`에, 소프트 삭제는 `test/soft-delete.test.ts`에 추가한다. 엔드포인트마다 다시 쓰지 않는다.
- 클라이언트는 Next.js 14 App Router, JSX(TypeScript 아님), Tailwind, Zustand. `lib/api.js`의 `api` 인스턴스만 쓴다. `npm run build`와 `npm run lint`가 통과해야 한다.
- 스키마를 바꾸면 `npx prisma migrate dev --name <name>`으로 마이그레이션을 만들고 `db:generate`를 돌린다. `db:push`는 쓰지 않는다.
- `prisma/seed.js`와 `docs/SEED_DATA.md`에 새 도메인의 시드를 더한다. CommonJS로 유지한다.
- 마지막에 `docs/API.md`, `docs/DATABASE.md`, `CLAUDE.md`를 새 구조에 맞게 고친다. CLAUDE.md는 "에이전트가 코드에서 추론할 수 없는 것"만 적는다.

## 작업 방식

- 브랜치 `feat/platform-expansion`에서 작업한다. push하지 않는다.
- 커밋은 의미 있는 단위(명세, 스키마+마이그레이션, 서버 구현+테스트, 클라이언트 화면 등)로 한다. 커밋 메시지는 한국어로 쓰고, 마지막 줄에 `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`을 붙인다.
- 도메인마다 계획 → 계획 검토 → 구현 → 검증(명세 대조 + 코드 리뷰 + typecheck/테스트/build) → 지적 반영 → 커밋 순으로 간다.
- 병렬로 일하는 워커는 각자 worktree와 테스트 DB(`bash scripts/test-db.sh workbridge_test_<이름>`)를 쓴다.
- 결정이 필요하면 가장 단순한 것이 아니라 실제 플랫폼에서 보편적인 쪽을 고르고, 그 결정을 `docs/expansion/DECISIONS.md`에 한 줄로 남긴다. 사람이 정해야 하는 것(제품 정책, 비용, 외부 서비스)만 오케스트레이터에게 올린다.
- 진행 상태는 `docs/expansion/PROGRESS.md`에 남긴다.
