# 버그 수정 (회귀 테스트 먼저)

버그를 고치는 PR에는 고치기 전 코드에서 실패하는 회귀 테스트가 있어야 한다(`CLAUDE.md`). 이 스킬은 그 테스트가
정말로 버그를 잡는지까지 확인하는 순서다. 기능 브랜치에서 한다.

## 1. 무엇이 버그인지 정하기

먼저 증상을 모은다.
- 이슈: `gh issue view <N>`. 버그 템플릿의 "재현 절차"와 "기대 동작과 그 이유"를 읽는다.
- 운영 오류: Sentry MCP로 그 오류의 스택과 요청 정보를 본다. 인증이 안 돼 있으면 사용자에게 `/mcp`에서 로그인하거나
  스택을 붙여 달라고 한다. 요청 id(응답 헤더 `X-Request-Id`)가 있으면 같은 `requestId`의 서버 로그 줄을 찾는다.
- 사용자 설명뿐이면 그 설명이 재현 절차다.

그다음 **기대 동작의 근거**를 찾는다. 근거는 셋이다. 이슈에 적힌 결정, `docs/domain/`의 결정, OpenAPI 문서
(`openapi.json`)의 상태 코드와 응답이다.
- 근거가 없거나 근거끼리 다르면 고치기 전에 멈추고 사용자에게 묻는다. 어느 쪽이 맞는지는 제품 결정이다.
- 지금 동작이 근거와 맞으면 버그가 아니라고 보고하고 끝낸다.

## 2. 실패하는 테스트로 재현하기 (수정보다 먼저)

**서버.** 재현은 곧 실패하는 vitest 테스트다. 그 라우트의 테스트 파일(`test/<domain>.test.ts`)에서 해당 `describe`
안에 넣는다. 테스트를 쓰는 규칙은 테스트 파일을 열면 `.claude/rules/tests.md`로 함께 들어온다. 테스트 DB가 없으면
`workbridge-server/`에서 `bash scripts/test-db.sh`로 만든다.

재현하기 까다로운 종류는 기존 테스트의 방법을 따른다.
- **경합(두 요청이 겹치는 순간):** 두 요청을 실제로 동시에 보내지 않는다. 대신 Prisma 함수에 spy를 건다. spy는
  다른 쪽 쓰기(예: 탈퇴)를 먼저 실행한 뒤 원래 함수를 그대로 부른다. 그러면 경합이 매번 같은 순서로 일어난다.
  예: `test/auth.test.ts`의 `select-role` 탈퇴 경합 테스트.
- **500:** 그 500을 낸 실제 입력으로 재현한다. 오류 처리 자체(로그, 롤백)의 버그일 때만 `test/helpers/faults.ts`의
  고장 주입을 쓴다.

**클라이언트.** 단위 테스트가 없으므로 회귀 테스트는 E2E 스펙이다. 그 흐름의 스펙(`workbridge-client/e2e/`)에
실패하는 단계를 더하거나 새 스펙을 만든다. 실행은 리포지토리 루트에서 `bash scripts/e2e.sh e2e/<spec>.spec.js`.
원인이 서버 응답이면 서버 테스트로 재현한다. 자동 테스트를 넣을 수 없으면 그 이유를 PR에 적고,
`run-workbridge` 스킬로 재현한 절차와 고치기 전 스크린샷을 남긴다.

## 3. 맞는 이유로 실패하는지 확인

수정하기 전에 새 테스트만 돌린다(`npx vitest run test/<file>.test.ts -t '<테스트 이름>'`). 실패 메시지가 버그 그
자체를 가리켜야 한다. 픽스처 오류, 오타, 타임아웃으로 실패하면 재현이 아니다. OpenAPI 응답 검사에서 실패할 때도
마찬가지다. 단, 응답에 문서에 없는 필드가 새는 것이 바로 그 버그라면 그 실패가 맞는 재현이다.

실패 메시지를 기록해 둔다. 보고와 PR에 쓴다.

## 4. 원인 고치기

- 증상이 아니라 원인을 고친다. 응답만 고쳐 보이게 하거나, 재현한 입력 하나만 피하는 `if` 문은 수정이 아니다.
- 같은 원인의 다른 곳을 찾는다. 빠진 `deletedAt: null`이나 조건 없는 재조회처럼 패턴으로 생긴 버그는 grep으로
  비슷한 코드를 확인한다. 같은 원인이면 함께 고치고 곳마다 회귀 테스트를 단다(예: #128은 Google 로그인과 역할
  선택의 같은 탈퇴 경합을 함께 고쳤다). 원인이 다르면 고치지 않고 보고한다.
- 기존 테스트가 버그 동작을 단언하고 있으면 그 단언을 고치기 전에 사용자에게 알린다.
- 응답의 상태 코드나 모양이 바뀌면 `src/openapi/`를 고친다. 1단계에서 사용자가 기대 동작을 새로 정했으면 그 결정과
  이유를 `docs/domain/`에 적는다.

## 5. 수정 뒤에 테스트를 바꿨다면 다시 증명

3단계에서 고치기 전 코드로 실패를 확인했으므로 보통은 이 단계가 필요 없다. 수정한 뒤 테스트를 고쳤다면, 고친
테스트가 여전히 버그를 잡는지 수정만 잠시 빼서 확인한다. `workbridge-server/`에서:

```bash
before=$(git stash list | wc -l)
git stash push -u -- src
if [ "$(git stash list | wc -l)" -gt "$before" ]; then
  npx vitest run test/<file>.test.ts -t '<테스트 이름>'
  git stash pop
else
  echo "stash가 만들어지지 않았다 — src에 변경이 없다"
fi
```

- 실패해야 한다(3단계와 같은 메시지). 통과하면 테스트가 버그를 잡지 못하는 것이니 3단계로 돌아간다.
- stash 개수를 비교하는 이유: `src`에 변경이 없으면 `git stash push`는 아무것도 넣지 않고도 성공(exit 0)을 돌려준다.
  그대로 `pop`하면 예전에 쌓인 다른 stash를 꺼낸다.
- stash한 동안에는 `src`를 편집하지 않는다(편집하면 훅이 고치기 전 코드로 `openapi.json`을 다시 만든다).

## 6. 검사

```bash
cd workbridge-server
npm run typecheck && npm run lint
npx vitest run test/<file>.test.ts            # 고친 도메인 전체
npm test                                       # 전체 스위트
```

클라이언트를 고쳤으면 `workbridge-client/`에서 `npm run lint && npm run build`, 그리고 2단계의 E2E 스펙.
DB가 없는 환경(GitHub의 `@claude` 작업)에서는 3·5단계와 테스트를 돌릴 수 없다. 그때는 실패 증명을 PR의 CI에
맡겼다고 보고한다.

## 7. 보고

- 원인 한두 문장과 그 근거(1단계의 문서·이슈)
- 회귀 테스트 이름과 고치기 전의 실패 메시지(3단계)
- 같은 원인으로 함께 고친 곳, 원인이 달라 남긴 의심 지점
- 돌린 검사

커밋은 사용자가 요청할 때 한다. 메시지는 `fix(server|client): <고친 뒤의 동작>`이고, 본문에 원인과 고친 방법,
회귀 테스트를 적는다(`git log --grep '^fix'`의 기존 커밋 참고). 이슈가 있으면 PR 본문에 `Closes #N`.
PR은 `pre-pr-review` 스킬로 연다.
